### B7 — r4010697013 (CodeRabbit security) — policy, explicit
Decision (matches asclearuc's review body): both `execute` paths report the driver's primary sentence and nothing else — the `[SQL:`/`[parameters:`/`LINE n:`/DETAIL/HINT/CONTEXT tails stay in the server log. What that does and does not guarantee is now stated precisely in the `_format_db_error` docstring and the READMEs: the primary sentence is passed through, so it can quote the statement fragment at the error position (`near "'x'": syntax error`, and pymysql/psycopg2 interpolate bound values client-side, so that fragment can carry one) or a value the statement carried or touched (PostgreSQL `invalid input syntax for type integer: "abc"`, MySQL `Duplicate entry 'x' for key …`). The justification is authorisation, not absence of data: the recipient holds `allow_execute` on the node and can read the same rows with a `SELECT`, so the diagnostic reveals nothing the caller could not already query. A generic fallback was not adopted because it removes the diagnostic this PR exists to provide, and redacting quoted tokens would also delete identifiers (MySQL quotes column names with single quotes: `Unknown column 'foo' in 'field list'`). Regression cases in {SHA} ({TESTS}) drive psycopg2-, pymysql- and clickhouse-shaped exceptions with `[SQL:`/`[parameters:`/stack-trace tails through both paths and assert the tails, the DETAIL key value and the bound parameter are absent while the constraint/column names survive; the syntax-error shape is pinned as passing the fragment through. If the maintainers want the stricter category-only contract instead, that is a one-line change to `_format_db_error` — leaving this thread open for that call.
