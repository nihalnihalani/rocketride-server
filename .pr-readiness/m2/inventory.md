### Caller-facing error policy (B7) — Fable decision
Both `execute` paths raise `RuntimeError('SQL execution failed: <driver primary message>')`. The primary message is the driver's own first sentence with every statement/parameter-bearing tail removed (`[SQL:`, `[parameters:`, `[cached since`, `(Background on this error`, `LINE n:`, `DETAIL:`, `HINT:`, `CONTEXT:`, `QUERY:`, `STATEMENT:`). The full exception stays in the server log (`error(...)`). Residual, accepted by design and stated in code + docs (corrected after the devil's-advocate pass): the driver's primary sentence is passed through, so it can quote the statement fragment at the error position (`near "'x'": syntax error`; pymysql/psycopg2 interpolate bound values client-side, so the fragment can carry one) or a value the statement carried or touched (PostgreSQL `invalid input syntax for type integer: "abc"` — which on INSERT…SELECT/CAST can be another row's value — MySQL `Duplicate entry 'x' for key ...`). Rationale is authorisation, not absence of data: the recipient holds `allow_execute` and can read the same rows with a SELECT. A generic redaction of quoted tokens would also delete identifiers (MySQL quotes column names with single quotes), destroying the diagnostic the maintainer asked for. Not adopted: CodeRabbit's generic fallback/category. The disagreement is stated on the thread and left for the reviewers to accept or overrule.
