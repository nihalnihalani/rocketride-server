## 2. Intended vs actual

**Intended:** ship a first-class Drizzle ORM driver whose SQL rides the RocketRide pipeline's `execute`/`begin`/`commit`/`rollback` tool functions instead of a TCP socket; deprecate (not remove) the Sequelize integration; make the server return positional rows so Drizzle's positional mappers work.

**Actual:** that, delivered competently — plus a second, less visible change: a **server-side transaction-semantics policy change that affects every existing consumer of the database tool**, not just Drizzle (commit 11, `4abc02cc3`, "keep tx session alive on failed statement"). The SDK half is careful, well-tested and structurally sound. The engine half changes failure/rollback semantics for the Sequelize shim, MCP/AI agents and direct SDK users, and carries this review's two highest-severity findings.

The client half is genuinely well built: it plugs into drizzle-orm's real driver contract (`PgSession` / `PgPreparedQuery` / `PgTransaction` / `PgQueryResultHKT` from `drizzle-orm/pg-core`), models itself explicitly on the stock `pg-proxy` and `node-postgres` sessions, documents each `@internal` runtime symbol it reaches past (`mapResultRow`, `queryWithCache`, `dialect`/`session`), and never string-interpolates a parameter value.

#### PR1908-F1 · **P1** · confidence **high** · INTRODUCED
**An engine that does not implement `row_mode` makes every Drizzle `select()` return blank rows, silently.**

- **Where:** `packages/client-typescript/src/client/drizzle/index.ts:63-65` (sends `rowMode: 'array'` for `method === 'all'` and unconditionally trusts the reply) → `packages/client-typescript/src/client/drizzle/session.ts:143-147` (`(rows as unknown[][]).map((row) => mapResultRow(fields!, row, …))`, positional indexing). Server side: `packages/ai/src/ai/common/database/db_instance_base.py:264-268` adds `row_mode` as a new optional `input_schema` property; the schema does not set `additionalProperties: false`, so an engine built before this PR simply ignores the field and returns object rows.
- **Trigger:** new SDK (`rocketride` with `./drizzle`) talking to any engine that predates this change — the normal state of the world for weeks/months after the npm package ships, since the SDK and the engine release on independent cadences (RELEASE.md §Packages lists them as separate artifacts).
- **Expected:** a clear, immediate error naming the missing engine capability.
- **Actual (executed):** `db.select().from(users)` resolves to `[{}]` — right row count, every column gone, **no error**.
- **Evidence:** review-only probe `/private/tmp/rv1908/probe/adapter-probe.test.ts`, fake `DrizzleDatabaseLike` that ignores `rowMode` and returns `[{ id: 1, name: 'ada' }]`. Output: `PROBE legacy-engine select -> [{}] threw: undefined`.
- **Production impact:** silent data loss on read. An application reads "1 row" with all fields `undefined`, writes derived state, and never sees an error. This is the worst failure shape available.
- **Smallest corrective direction:** one runtime guard in `makeTransport` — when `method === 'all'` and `res.rows.length > 0 && !Array.isArray(res.rows[0])`, throw `Error("this pipeline's engine does not support rowMode: 'array' (upgrade the engine to use rocketride/drizzle)")`. ~4 lines, no protocol change. A capability probe via the existing `dialect` tool would be nicer but is not required.
- **Regression-test criterion:** a driver test whose transport returns object rows for `method: 'all'` must **reject with a message naming `rowMode`**, not resolve.

#### PR1908-F2 · **P1** · confidence **high** (mechanism executed on sqlite; Postgres specifics reasoned from the PR's own comment) · INTRODUCED
**Removing the auto-rollback on a failed session statement turns a loud failure into a silent discarded commit.**

- **Where:** `packages/ai/src/ai/common/database/db_instance_base.py:296-310` — the diff deletes the `except Exception:` block that used to call `tx_registry.rollback(session_id)` and re-raise. Commit `4abc02cc3`.
- **Trigger:** any consumer that catches a statement error inside an open session and then commits. Concretely reachable from `db.transaction(async (tx) => { try { await tx.insert(...) } catch { /* handled */ } ... })`, and from every non-Drizzle consumer of `begin`/`execute`/`commit` (Sequelize shim, MCP tools, AI agents).
- **Expected:** `commit` must not report success for a transaction the database discarded.
- **Actual (executed):** `TransactionRegistry.begin → execute(unique violation) → commit` — `commit()` returns normally, no error reaches the client. On Postgres the transaction is additionally **aborted**, so `COMMIT` is answered with `ROLLBACK` and every write is discarded while the client is told `{ok: true}`. **The PR's own comment states this:** `db_instance_base.py` — *"Postgres marks the transaction aborted (commit degrades to rollback)"* — and then does not surface it.
- **Evidence:** `/private/tmp/rv1908/py_probe.py` (loads `tx_registry.py` directly, real SQLAlchemy 2.0.46 + in-memory sqlite with the standard SAVEPOINT recipe): `PROBE commit-after-failed-statement -> OK: statement error=IntegrityError; commit() returned normally (no error surfaced to the client)`. Before this PR, the same sequence raised `unknown or expired transaction session` on commit — asserted by the test the PR **rewrites**: `packages/ai/tests/database/test_execute_session.py`, `test_session_execute_overflow_releases_session` → `test_session_execute_overflow_keeps_session_alive`, replacing `pytest.raises(ValueError, match='unknown or expired')` with `assert inst.rollback(...) == {'ok': True}`.
- **Production impact:** silent data loss on write for any consumer that handles statement errors in-transaction. Regression in blast radius: affects consumers that have nothing to do with Drizzle.
- **Note on Drizzle's own happy path:** `PipesSession.transaction` (session.ts:206-221) propagates the callback error and rolls back, so Drizzle's *unhandled* path is safe. The hazard is user code that handles the error, and every direct tool consumer.
- **Smallest corrective direction:** add a `failed: bool` flag on `_Held`, set it in `execute()`'s error path, clear it on a successful `rollback` / `rollback to savepoint`, and make `TransactionRegistry.commit()` raise (`ValueError('cannot commit: session has a failed statement; roll back or roll back to a savepoint first')`) while it is set. The savepoint recovery path (verified working, below) already clears the condition correctly.
- **Regression-test criterion:** `begin → failing statement → commit` must raise; `begin → savepoint → failing statement → rollback to savepoint → commit` must succeed.

#### PR1908-F3 · **P2** · confidence **high** · INTRODUCED
**A failed statement now pins a pooled database connection for ≥300 s, and a retry loop pins it indefinitely.**

- **Where:** `packages/ai/src/ai/common/database/tx_registry.py:236-237` — `finally: held.last_used = self._clock()` refreshes the idle clock *even when the statement raised* (deliberate; asserted by the new `test_failed_statement_still_refreshes_last_used`). Combined with `tx_registry.py:194` — `reap_idle()` is invoked **only** from `begin()` — and the 300 s default (`tx_registry.py:180`, `db_global_base.py:469`).
- **Expected:** an abandoned session releases its connection promptly.
- **Actual:** a client that errors and disconnects holds the connection until *another* `begin()` arrives on that node — potentially forever on a quiet node. A client that retries a failing statement every <300 s never ages out at all.
- **Evidence:** read of the reaper call-site (single call at line 194) plus the PR's own test and the docs' own admission (`database-drizzle.md:144`: *"the reaper is lazy and only sweeps stale sessions the next time a transaction starts on that node"*).
- **Production impact:** connection-pool exhaustion under an error-looping client. Pre-PR the failed statement released the connection immediately.
- **Smallest corrective direction:** either call `reap_idle()` from `execute`/`commit`/`rollback` as well, or add an absolute session-lifetime cap independent of `last_used`.
- **Regression-test criterion:** a session whose only activity is repeated failing statements must be reaped after an absolute lifetime cap.

#### PR1908-F4 · **P2** · confidence **high** · PRE-EXISTING code, newly load-bearing
**Result-type fidelity: numerics lose precision, int8 > 2^53 loses precision, bytea is lossily decoded — and the documented limitation covers only binary *parameters*.**

- **Where:** `packages/ai/src/ai/common/database/db_instance_base.py:399-405` — `if hasattr(val, '__float__'): return float(val)` (before the `isoformat` branch), and `if isinstance(val, bytes): return val.decode('utf-8', errors='replace')`.
- **Evidence (executed, `/private/tmp/rv1908/py_probe.py`):**
  - `Decimal('12345678901234567890.1234567890')` → `1.2345678901234567e+19` (float) — **~13 significant digits lost.** Drizzle's `numeric()` column is typed `string` in TS; it receives a lossy float.
  - `b'\x00\x01\xff\xfe'` → `'\x00\x01??'` (U+FFFD replacement chars) — unrecoverable.
  - `int8` `9007199254740993` is emitted exactly by Python, but the wire is JSON and the client parses with `JSON.parse` (`TransportWebSocket.ts:279`). Executed in node: `{"v":9007199254740993}` → `9007199254740992`; `BigInt(parsed)` → `9007199254740992`. Drizzle's `bigint({mode:'bigint'})` `mapFromDriverValue` is `BigInt(value)` — it cannot recover.
  - Working correctly: `dict`/`list` → JSON string, which drizzle's `jsonb.mapFromDriverValue` `JSON.parse`s back (verified at `node_modules/drizzle-orm/pg-core/columns/jsonb.js:24-30`); `datetime` → ISO string, which drizzle's `timestamp` accepts.
- **Why it matters now:** before this PR the only consumer was a raw-SQL tool. This PR markets the path as a typed ORM with `numeric`, `bigint` and `bytea` column types, and its own e2e header claims *"Serialization — dates/numerics survive the JSON transport"* (`drizzle-e2e.test.ts:47`). That test asserts only `1.5::numeric` (`drizzle-e2e.test.ts:289`) and its own comment concedes *"numerics as floats"* — the claim is not supported by the test.
- **Documented limitation is one-sided:** `database-drizzle.md:183-185` disclaims binary **parameters** ("the server rejects them with a bind error"). Binary **results** are silently mangled and undocumented.
- **Smallest corrective direction:** in `_sanitize_value`, emit `Decimal` as `str(val)` and `int` outside ±(2^53−1) as `str(val)` (both are what drizzle's `numeric`/`bigint({mode:'bigint'})` mappers already expect); base64-encode or reject `bytes`. At minimum, extend the Limitations section to cover numeric precision, int8 range and bytea results.
- **Regression-test criterion:** round-trip `numeric(38,10)`, `bigint` at `2^53+1`, and a `bytea` through the adapter and assert exact equality.

#### PR1908-F5 · **P3** · confidence **high** · INTRODUCED
**`_rewrite_placeholders` mis-detects `E'…'` escape strings, leaving `$n` unbound after any token ending in `e`/`E` that abuts a quote.**

- **Where:** `packages/ai/src/ai/common/database/tx_registry.py:39` — `is_escape_string = out and out[-1] and out[-1][-1] in 'eE'`. `out[-1]` is the previously emitted character, so `LIKE'…'` and `ELSE'…'` (both legal Postgres with no intervening space) are treated as escape strings, and backslash-escape scanning mis-locates the closing quote.
- **Evidence (executed):** `to_sqlalchemy_text("select * from t where v LIKE'a\\' and id = $1", [1])` → `("select * from t where v LIKE'a\\' and id = $1", {})` — `$1` **not** rewritten, `binds` empty. Same for `else'x\\'`. The control case `select 'a\\', $1` (space before the quote) binds correctly: `('select \'a\\\', :b1', {'b1': 1})`.
- **Production impact:** low. The statement reaches the driver with a literal `$1` and no bind → a loud driver error, never silent corruption. Drizzle's generated SQL always puts a space before literals, so the Drizzle path is unaffected; the exposure is hand-written SQL through `DatabaseApi.query`.
- **No injection risk:** values are never inlined. Verified across the whole rewrite — every branch either copies text through or emits `:bN` with `binds[key] = params[idx-1]`, and SQLAlchemy `text()` binds server-side. The only string-interpolation boundaries in the entire PR are savepoint names (`session.ts:234`, `sp${this.nestedIndex + 1}`, generated internally from an integer — not attacker-influenced) and the `$n → :bN` key names.
- **Smallest corrective direction:** require a token boundary — e.g. test the accumulated tail against `(?<![A-Za-z0-9_$])[eE]$` instead of a bare last-character check.
- **Regression-test criterion:** add `("select * from t where v LIKE'x' and id = $1", [1])` to the existing `test_placeholder_rewrite_skips_quoted_regions` parametrisation and assert `binds == {'b1': 1}`.

#### PR1908-F13 · **P2** · confidence **high** · INTRODUCED (inherent to the design)
**Ambiguous commit: a lost commit response is reported as failure, and a retry double-applies the writes.**

- **Where:** `packages/client-typescript/src/client/drizzle/session.ts:211-221`.
- **Actual (executed):** when `commit()` rejects, the driver calls `transport.rollback(sessionId)` (best-effort, swallowed) and rethrows the commit error — `PROBE commit-failure -> threw: Error: unknown or expired transaction session: sid-1 rollbackCalls: 1`.
- **Impact:** if the commit **succeeded** server-side and only the reply was lost (socket drop, timeout), the caller sees a rejection for a committed transaction. There is no commit-status query, no idempotency key, and no `sessionId`-scoped "was this committed?" tool. A caller that retries duplicates every write. This is the direct answer to *"can reconnect-or-retry duplicate writes?"* — **yes**, and nothing in the SDK or the docs says so.
- **Smallest corrective direction:** document it prominently (cheapest), and/or add a `tx_status(session_id)` tool so a client can disambiguate after a transport failure.
- **Regression-test criterion:** a test asserting the documented contract — that a rejected `db.transaction()` does **not** guarantee the transaction was rolled back.

## 6. Compatibility + operational implications

**Dependencies.** Minimal and clean: one package, `drizzle-orm@0.45.2`, zero transitive runtime deps, optional peer + devDependency, one importer, no existing resolution disturbed. 90 of the 97 lockfile lines are optional-peer metadata. Release impact on the published tarball: none (peer deps are not bundled; `npm pack` produced `rocketride-1.3.0.tgz`, 304 files, 2.3 MB, in run #5). Only F12 (peer range) is worth touching.

**Deprecation policy.** I looked for one and it does not exist as a written policy: `RELEASE.md` contains **zero** occurrences of "deprecat", and neither `CONTRIBUTING.md` nor `AGENTS.md` defines a deprecation window. The de facto policy is the **frozen contract machinery** — "nothing ever frozen can be removed", enforced by per-version tsc floors and the regen-must-be-a-no-op CI guards. Against that de facto rule, this PR is **correct and conservative**: commit 7 removed Sequelize outright (would have broken the v0/v1 shell floors and the v1.3 client floor), commits 24/25 escalated to a 2.0.0 + contract reset, commits 28/29/30 walked all of it back. The final state — `@deprecated` JSDoc, surface retained, `database-sequelize.md:6-9` banner saying removal only "in a coordinated major release" — is exactly what the contract system demands. **No compatibility window is violated.**

**Migration path.** This is the gap. The PR deprecates the only existing ORM integration and ships **no migration guidance whatsoever** (F10): zero mentions of Sequelize in the new guide, no concept mapping, no back-link. The deprecation banner tells users to move and does not tell them how. For a "Sequelize deprecated" PR, that is the substantive documentation defect.

**Cross-version operational risk (the big one).** The SDK ships to npm and the engine ships as a binary, on independent release trains (RELEASE.md §Packages). This PR's client half **hard-depends** on the server half (`row_mode`) with **no negotiation**, and the failure mode is silent blank rows (F1). Operationally: the day the new SDK hits npm, every user whose engine predates the merge gets silently empty query results. This alone justifies the ordering in the split recommendation.

**Blast radius beyond Drizzle.** The `packages/ai` changes alter behaviour for **every** consumer of the database tool: `_sanitize_value` now emits JSON strings for `dict`/`list`/`tuple` where it previously emitted Python `repr` (a fix, but a wire-format change for the Sequelize shim, MCP tools and AI agents); and the failed-statement policy change (F2/F3) changes rollback and connection-lifetime semantics for all of them. None of this is mentioned in the PR title, and the Sequelize shim's own tests were touched only for a typing detail.

### Merge as ONE, or split? — **Split into two ordered PRs.**

**Why size alone is not the argument.** The +13,638 headline is 85.8% one mechanically generated contract snapshot whose semantic delta is 145 lines, plus 97 lines of lockfile. The actual hand-written production surface is **609 lines**. By review-ability, this PR is small. "Split out the generated file" is not an available option.

**The real seam is engine vs. SDK, and it is a good one:**

- **Risk isolation.** The two P1s live on opposite sides. F1 is a client-side compatibility bug; F2/F3 are an engine-side semantics regression affecting consumers that have nothing to do with Drizzle. - **Rollback granularity.** The engine and the npm SDK ship on separate trains. Reverting the SDK does **not** revert the engine. Today they are welded into one revert unit that spans both.
- **Correct deployment ordering.** The client half hard-depends on the server half. Merging them together does not make them *deploy* together — and F1 is the cost of that gap.
