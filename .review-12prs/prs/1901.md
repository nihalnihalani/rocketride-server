## 3. Intended behaviour vs actual implementation

**Bug (issue #1837).** `RocketRideClient.__init__(self, uri='', auth='', **kwargs)` read the options it
knows by name via `kwargs.get(...)` and silently discarded everything else. A typo like `client_nmae`
behaved exactly as if no option had been passed; the symptom ("the setting didn't take") appears far
from the call site. The class docstring's `Raises:` section implied input was validated.

**Implementation.** A module-level `_KNOWN_CONSTRUCTOR_KWARGS` frozenset of 16 names
(`client.py:78-101`) and, as the first statement of `__init__` before the environment, URI or any
client state is touched (`client.py:191-196`):

```python
unknown = set(kwargs) - _KNOWN_CONSTRUCTOR_KWARGS
if unknown:
    names = ', '.join(sorted(unknown))
    raise TypeError(f'RocketRideClient.__init__() got unexpected keyword argument(s): {names}')
```

Plus `TypeError` added to both `Raises:` sections and eight previously-undocumented options
(`client_name`, `client_version`, `public`, `on_trace`, `on_event`, `on_connected`, `on_disconnected`,
`on_connect_error`) added to the `**kwargs` docstring.

**Allowlist correctness — verified exhaustively.** I enumerated every option the constructor chain
actually consumes:

| source | options |
|---|---|
| `client.py:166-255` (`kwargs.get`/`pop`) | `env`, `ws_path`, `client_name`, `client_version`, `on_trace`, `public`, `module` |
| `mixins/connection.py:78` (named params) | `persist`, `max_retry_time` |
| `mixins/events.py:97-102` | `on_event`, `on_connected`, `on_disconnected`, `on_connect_error`, `on_protocol_message`, `on_debug_message` |
| `core/dap_client.py:86` | `request_timeout` |
| `core/dap_base.py:151` | `transport` |

The allowlist is exactly this set **minus `transport`**. Nothing consumed is missing, so no working
option is broken. Cross-checked against the documented config surface: every field of
`RocketRideClientConfig` (`types/client.py:157-190`) is accepted, and `RocketRideClient(**config)`
still works (measured, §5-C).

### P2

**PR1901-F3 — a subclass that forwards its own keyword through `super().__init__()` now raises.** (confidence: high — reproduced)

* `client.py:193-196`. Measured (§5-C):

  ```
  class PassThroughClient(RocketRideClient):
      def __init__(self, *a, **kw):
          self.tag = kw.get('tag')          # reads but does not remove
          super().__init__(*a, **kw)

  develop  -> ACCEPTED
  #1901    -> TypeError: got unexpected keyword argument(s): tag
  ```

  The disciplined variant (`def __init__(self, *a, my_option=None, **kw)`, which consumes its own
  keyword before forwarding) still works on both — measured.
* This is a legitimate Python extension pattern, and the class is explicitly built for extension
  (six mixins, `**kwargs` all the way down). Nothing in this repository does it —
  `packages/client-mcp`, `packages/ai/src/ai/modules/{mcp,task_http}`, `nodes/test/conftest.py` and
  the CLI all construct `RocketRideClient` directly with known options only — so in-repo breakage is
  **zero**. External subclasses are unmeasurable.
* Pre-existing tolerance removed deliberately; the PR body flags the forward-compat aspect
  (*"forward-compat callers passing extra kwargs now get a loud error. that's the point of the issue;
  a warning-only variant is the smaller step if maintainers prefer it"*) but not this specific pattern.
* Direction: nothing is required if maintainers accept the trade. If softening is wanted, the author's
  own suggestion (`DeprecationWarning` for one minor version, then raise) is the standard path, and
  either way the class docstring should say that subclasses must consume their own keywords.
* Regression-test criterion: a test for both subclass patterns, asserting whichever behaviour is chosen.

**PR1901-F4 — the allowlist is a hand-maintained duplicate of five `__init__` signatures.** (confidence: high)

* `client.py:78-101` restates, by hand, what `RocketRideClient.__init__`, `ConnectionMixin.__init__`,
  `EventMixin.__init__`, `DAPClient.__init__` and `DAPBase.__init__` consume. It is correct **today**
  (verified name by name, §3) — but any future option added to a mixin must be added in two places,
  and forgetting turns a newly-documented option into a hard `TypeError`.
* The failure is silent at authoring time and loud only for the user, which is the same class of
  problem #1837 complains about, inverted.
* Direction (architecture, not blocking): derive the set from the MRO at import time — walk
  `type(self).__mro__`, collect each `__init__`'s named parameters via `inspect.signature`, and union
  with the handful this constructor reads out of `**kwargs`. That is self-maintaining and would also
  make the `transport` case explicit rather than a silent omission. At minimum, add a comment on each
  mixin `__init__` pointing at the allowlist.

### P3

**PR1901-F5 — the `transport` test's justification is factually wrong.** (confidence: high)

* `tests/test_client_constructor_kwargs.py:51-53` states: *"the DAP base chain never consumes a
  caller-supplied transport, so passing one must be rejected rather than silently forwarded"*.
  The DAP base chain **does** consume it — `core/dap_base.py:151: self._transport = kwargs.get('transport', None)`.
* The real reason a caller cannot pass `transport` is that `client.py:258` calls
  `super().__init__(transport=None, module=module, **kwargs)`, so a caller's `transport` collides.
  Measured on develop (§5-C): `TypeError: ConnectionMixin.__init__() got multiple values for keyword
  argument 'transport'`. So `transport` was **already** rejected; this PR only improves the message.
* Worth correcting because the comment is the stated justification for excluding a kwarg the base
  class genuinely reads — a future maintainer could "fix" the omission on the strength of it.

**PR1901-F6 — test style and coverage gaps.** (confidence: high)

* `tests/test_client_constructor_kwargs.py` uses bare `try/except/else: raise AssertionError(...)`
  in all four tests where every other test file in the package uses `pytest.raises`
  (e.g. `tests/test_deploy_unit.py`, `tests/test_send_files_concurrency.py`).
* Not covered: the two subclass patterns (F3); `RocketRideClient(**config)` with the documented
  `RocketRideClientConfig` TypedDict; and a guard that the allowlist stays in sync with the mixin
  signatures — the last of which is the test that would actually prevent F4 from biting.

## 6. Compatibility + operational implications

* **Deliberate breaking change**, correctly identified as such by the author. Callers passing an
  unknown keyword — a typo, a future option, or a subclass keyword forwarded by accident — now get a
  `TypeError` at construction instead of silent no-op behaviour. That is the point of #1837.
* `TypeError` is the idiomatic Python answer and matches what CPython raises for an unexpected keyword
  on a normal signature, so the exception type is right (and, unusually for this SDK, does not need an
  entry in `core/exceptions.py`). The message names every offending key, sorted — genuinely actionable.
* **No documented option is affected.** All 13 `RocketRideClientConfig` fields and all 9
  docstring-only options still work (measured).
* The `**kwargs` docstring gains eight previously-undocumented options, which is a real documentation
  improvement independent of the validation.
* Same-build note: `packages/client-python/src/rocketride` is synced into `dist/server/rocketride`
  (`packages/client-python/scripts/tasks.js`), so the engine's own `RocketRideClient` constructions are
  subject to this check. All were verified compliant (§5-E).
* Not flagged: no `CHANGELOG.md` entry for a breaking change; the class docstring does not tell
  subclass authors they must consume their own keywords.

## 7. Dependencies / overlap / rebase status

* **Needs reconstruction on develop, not a rebase.** A plain `git rebase develop` would replay all 96
  commits; the 91 duplicates would mostly become empty and be dropped, but the operation is noisy and
  error-prone. See `branch-recovery-1901.md` for the recommended route.
* No file overlap with #2011 / #2007 / #2004 / #1895.
* **Sequencing:** because this validates `RocketRideClient.__init__`, any *other* PR that adds a new
  constructor keyword must add it to `_KNOWN_CONSTRUCTOR_KWARGS` in the same change, or that option
  becomes a hard `TypeError`. Whichever of the two merges second needs the pairing. I checked the
  Python-side PRs in this review batch: **none of #2011, #2007, #2004, #1895 adds a constructor
  keyword**, so within this batch there is no conflict.

## 8. Unresolved questions

1. Hard `TypeError` or a `DeprecationWarning` grace period? The author explicitly offers the
   warning-only variant as the smaller step. Maintainer call; #1837 reads as wanting the loud error.
2. Should the allowlist be derived from the MRO instead of hand-maintained (F4)?
3. Is the "subclass forwards its own keyword" break (F3) acceptable? It has zero in-repo impact but is
   a real Python pattern.
4. Does this need a `CHANGELOG.md` entry and a note in the class docstring for subclass authors?

## 9. Verdict — **REBUILD OR SPLIT**

The change itself is small, correct and well-targeted. The allowlist is complete against every option
the constructor chain consumes (verified name by name), the check runs before any state is built, the
message names every offending key, no documented option regresses, and the docstring gains nine
options it should always have had. On the code alone this would be close to ready.

It cannot merge in this form. The branch carries 91 patch-equivalent duplicates of develop's own
commits, which would pollute develop's history and which make the PR unreviewable (609 files shown for
a 108-line change). CI is also red on a trailing blank line.

Remaining work:

   `branch-recovery-1901.md` for the exact commits, the ordering, and the post-reconstruction checks.
   Do **not** rebase or cherry-pick all 96 commits.
2. Delete the trailing blank line at
   `packages/client-python/tests/test_client_constructor_kwargs.py:61`, then `ruff format --check`. (F2)
3. Correct the `transport` comment at `tests/…:51-53` — the DAP base chain *does* read `transport`
   (`core/dap_base.py:151`); the collision comes from `client.py:258`. (F5)
4. Decide §8 Q1 (hard error vs deprecation window) with a maintainer.
5. Recommended, not blocking: add tests for both subclass patterns and for
   `RocketRideClient(**RocketRideClientConfig)`, switch to `pytest.raises`, and add a test that the
   allowlist still matches the mixin signatures (F4/F6). Add a `CHANGELOG.md` entry and a docstring
