## 2. Intended contract vs. actual

**Intent:** the local engine runs with `--port=0` (`apps/vscode/src/engine/local/engine-local.ts:157`), so its port changes on every restart. Workspace `.env` auto-sync only helps a script reading *this* workspace's `.env`. Publish the resolved URI to a fixed, workspace-independent file so any process on the machine can find the live engine.

**Actual data flow, traced end to end:**

| Hop | Location | Verified |
|---|---|---|
| Engine spawned with `--host=127.0.0.1 --port=0` | `engine-local.ts:146-158` | yes |
| Port learned by parsing uvicorn stdout `/Uvicorn running on https?:\/\/[\w.]+:(\d+)/` | `engine-local.ts:346-350` | yes |
| Discovery written **at readiness**, after `processReady = true` | `engine-local.ts:352-355` → `:445-462` | yes |
| Written to `connectionDiscoveryPath(this.installer.dir)` = `<parentDir>/engine/connection.json` | `connectionDiscovery.ts:75-77`, `engine/shared/engine-installer.ts:103,131-133` | yes |
| `parentDir` = `getUserConfigDir()` | `extension.ts:252`, `connection/connection.ts:667` → `engine-manager.ts:223` | yes |
| Removed on child `exit`, only if the file's `pid` is still ours | `engine-local.ts:322-323` → `:468-476` | yes |
| Python reads `<get_user_config_dir()>/engine/connection.json` | `_connection_discovery.py:76-78` | yes |
| Path agreement across languages | **executed, byte-for-byte match** — see E5/E6 | yes |
| Client uses it as last-resort URI **and** auth | `client.py:204-222` | yes |

**Contract format:** `{"uri": str, "apiKey": str, "pid": number, "updatedAt": ISO string}`, pretty-printed + trailing newline. Both parsers require only `uri: string` and `pid: number`; `apiKey`/`updatedAt` default to `''`; unknown fields ignored (forward-compatible). Both sides tolerate a missing/malformed file by returning `null`/`None`.

**The gap between intent and implementation:** the stated intent is *discovery* — "here is where the engine is". The implementation is *discovery **and** credential adoption* — `client.py:219-222` also takes the file's `apiKey` as the client's credential when none was supplied. Nothing in the file is validated as loopback. That widening is the source of the two highest-severity findings.

## 4. Findings

### PR1874-F1 — the discovery file can redirect a caller's credential to an arbitrary remote host — **P1**, confidence high (reproduced)
- **File:line:** `packages/client-python/src/rocketride/client.py:204-222`; `packages/client-python/src/rocketride/_connection_discovery.py:100-128`; `apps/vscode/src/engine/local/connectionDiscovery.ts:96-116`.
- **Trigger:** any `RocketRideClient()` constructed without an explicit `uri` and without `ROCKETRIDE_URI`, while a `connection.json` exists whose `uri` names a non-loopback host and whose `pid` is live.
- **Expected:** a *local engine discovery* fallback should only ever produce a loopback URI.
- **Actual (reproduced, E3):** with `ROCKETRIDE_APIKEY=sk-users-cloud-key` in the environment and a discovery file containing `{"uri": "https://attacker.example.com", "pid": <live>, ...}`, the constructed client is `uri='wss://attacker.example.com:5565/task/service' apikey='sk-users-cloud-key'`. The caller's cloud credential is now aimed at a host named by a file on disk.
- **Production impact:** anything running as the user that can write `~/Library/Application Support/RocketRide/engine/connection.json` (macOS) / `~/.config/RocketRide/engine/connection.json` (Linux) / `%LOCALAPPDATA%\RocketRide\engine\connection.json` (Windows) silently redirects every credential-bearing SDK client that relies on the environment for auth and on the default for the URI. The blast radius is bounded to same-user code — a real mitigation — but the path is fixed, well-known, workspace-independent, created with default permissions (F2), and never validated. Compare the client's own documented warning at `packages/client-python/docs/index.md:44` about silent transport downgrades: this is the same class of silent, security-relevant redirection, one layer up.
- **Introduced.**
- **Corrective direction:** (1) in `read_connection_discovery()`, reject any `uri` whose host is not `localhost` / `127.0.0.1` / `::1` — and mirror it in `parseConnectionDiscovery`; (2) do **not** adopt the file's `apiKey` as a credential (F3); (3) consider gating the whole fallback behind an opt-in (`ROCKETRIDE_DISCOVER_LOCAL=1`) so it is never a silent default.
- **Regression-test criterion:** a discovery file naming a non-loopback host must be ignored, and the resulting client must fall back to the cloud default.

### PR1874-F2 — the file carries a credential and is written with default permissions, though the repo writes 0600 elsewhere — **P2**, confidence high
- **File:line:** `apps/vscode/src/engine/local/engine-local.ts:449-461` (`fs.writeFileSync(path, text)` — no `mode`, so 0o666 & ~umask, typically 0644).
- The same codebase writes credential-bearing files with `{ encoding: 'utf8', mode: 0o600 }` — `apps/vscode/src/engine/service/service-linux.ts:118,158`; `service-mac.ts:100,137`. The discovery file contains an `apiKey` field and determines where a credential is sent, so it belongs in that category.
- **Production impact:** on a multi-user or shared machine the file is world-readable, and the directory's permissions are whatever `EngineInstaller` created.
- **Introduced.** **Corrective direction:** `fs.writeFileSync(p, text, { encoding: 'utf8', mode: 0o600 })`.

### PR1874-F3 — a client with no `auth` silently authenticates with the hardcoded `'MYAPIKEY'` — **P2**, confidence high (reproduced)
- **File:line:** `packages/client-python/src/rocketride/client.py:219-222`; value written at `apps/vscode/src/engine/local/engine-local.ts:454`.
- **Expected (pre-PR):** `RocketRideClient()` with no auth leaves `_apikey = None`; `connect()` then fails with an explicit missing-credential error.
- **Actual (reproduced, E3):** `live local entry, no env → uri='ws://localhost:54321/task/service' apikey='MYAPIKEY'`.
- **Production impact:** a credential appears from nowhere. It is the well-known local default (`connection/connection.ts:273`), so exposure is low; the problem is that credential resolution now has an invisible fourth source, and a user who *changed* their local API key gets a confusing auth failure instead of a clear "no credential configured".
- **Introduced.** **Corrective direction:** drop the `apiKey` from both the file and the client fallback — the file's job is the port. If it must stay, require an explicit opt-in.
- **Regression-test criterion:** with a valid discovery file and no auth anywhere, `_apikey` stays `None`.

### PR1874-F4 — `os.kill(pid, 0)` is not a liveness probe on Windows — **P1**, confidence high (code inspection; **not executable on this macOS host**)
- **File:line:** `packages/client-python/src/rocketride/_connection_discovery.py:86-99`.
- The module explicitly supports Windows (`get_user_config_dir()` branches on `sys.platform == 'win32'`, `:65-67`) and the docs promise the reader verifies liveness (`apps/vscode/docs/usage.md`, "verifying the recorded PID is still alive first").
- CPython implements `os.kill` on Windows by calling `TerminateProcess(handle, sig)` for **any** signal other than `CTRL_C_EVENT` / `CTRL_BREAK_EVENT`. Signal 0 is a POSIX idiom that does not port: on Windows it is a request to terminate, not to probe. `ProcessLookupError` is likewise POSIX-only — a missing PID on Windows raises a generic `OSError`, which the `except OSError: return True` branch (`:95-97`) treats as **alive**.
- **Consequence if the TerminateProcess reading is right:** constructing a `RocketRideClient()` on Windows with no URI configured would kill the running local engine. Even if it is wrong, the fallback branch still makes every dead PID look alive on Windows, so the stale-entry protection the docs promise does not exist there.
- **Contrast within this same PR:** the TypeScript side does the equivalent check correctly — `process.kill(pid, 0)` at `engine-local.ts:231` and `engine-installer.ts:836`, which Node documents as *"a platform independent way to test for the existence of a process"* (nodejs.org/api/process.html, `process.kill`). The Python module's claim to mirror the extension does not survive the port.
- **Introduced.**
- **Corrective direction:** on `sys.platform == 'win32'`, either skip the liveness check entirely (return `True` — "can't tell", matching the module's stated philosophy) or use `ctypes` `OpenProcess(SYNCHRONIZE, …)` + `WaitForSingleObject`. `psutil` is not a client-python dependency (`packages/client-python/pyproject.toml:41-46`) and should not become one.
- **Regression-test criterion:** a Windows CI job asserting `_is_process_alive(<pid of a live sentinel>)` is `True`, `_is_process_alive(<dead pid>)` is `False`, and — critically — that the sentinel is **still running afterwards**.
- **Verification recipe for whoever has a Windows runner:** start `python -c "import time; time.sleep(60)"`, note its PID, call `_is_process_alive(pid)` from another process, then check the sentinel's exit code.

### PR1874-F5 — a running local engine silently overrides the documented cloud default; SDK docs not updated — **P2**, confidence high (reproduced)
- **File:line:** `packages/client-python/src/rocketride/client.py:204-217`.
- Before: `uri = self._env.get('ROCKETRIDE_URI', CONST_DEFAULT_WEB_CLOUD)` — the documented default is `https://api.rocketride.ai` (`core/constants.py:66`). After: an existing discovery file wins over that default.
- **Reproduced (E3):** `live local entry, no env → ws://localhost:54321/task/service`.
- **Production impact:** a developer with the VS Code extension's local engine running and a script that relied on the cloud default now silently talks to localhost — a wrong-target failure that presents as puzzling empty results rather than a connection error.
- **Docs divergence:** `packages/client-python/docs/index.md` still says the URI comes from `uri` or `ROCKETRIDE_URI` (`:109`, `:123` — *"Raises ValueError if both `uri` and `ROCKETRIDE_URI` are empty"*). The PR documents the new behaviour only in `apps/vscode/docs/usage.md`. Per `AGENTS.md`'s co-located-documentation rule, a change to a public Python SDK behaviour belongs in `packages/client-python/docs/`. **This is a rule violation as written.**
- **Introduced.** **Corrective direction:** update `packages/client-python/docs/index.md` (resolution order and the `ValueError` sentence), and strongly consider making the fallback opt-in.

### PR1874-F6 — `ROCKETRIDE_URI=''` no longer raises — **P3**, confidence high (reproduced)
- **File:line:** `packages/client-python/src/rocketride/client.py:212`.
- **Reproduced (E4):** develop → `ValueError: Invalid URI '': missing hostname`; PR → `uri='wss://api.rocketride.ai/task/service'`.
- A deliberately-emptied env var used to fail loudly and now resolves silently. CI is known to pass empty strings for the sibling variable (`.github/workflows/_build.yaml:274`, and `packages/client-python/scripts/tasks.js:203-208` compensates for exactly this for `ROCKETRIDE_APIKEY`), so an empty `ROCKETRIDE_URI` is a realistic configuration.
- **Introduced**, arguably an improvement, but undocumented and untested. **Corrective direction:** decide deliberately, document it, and add a case.

### PR1874-F7 — neither parser validates `pid`; `0`, negatives and JSON `true` pass the liveness gate — **P3**, confidence high (reproduced)
- **File:line:** `_connection_discovery.py:114` (`isinstance(pid, int)`) and `connectionDiscovery.ts:105` (`typeof pid !== 'number'`).
- **Reproduced (E3, E5):** `pid: 0` → treated alive (POSIX `kill(0, 0)` probes the caller's whole process group); `pid: -1` → treated alive (`kill(-1, 0)` probes every process the caller may signal); `pid: true` → accepted, because `isinstance(True, int)` is `True` in Python. TS `parseConnectionDiscovery` also accepts `0`, `-1` and `1.5`.
- **Production impact:** a corrupt or hand-edited file bypasses the stale-entry protection and hands out a dead URI. Modest on its own; it removes the mitigation that F1's severity partly rests on.
- **Introduced.** **Corrective direction:** require `isinstance(pid, int) and not isinstance(pid, bool) and pid > 0`; `Number.isInteger(pid) && pid > 0` on the TS side.

### PR1874-F8 — PID reuse and VS Code crash leave a usable-looking stale entry — **P3**, confidence medium
- **File:line:** cleanup only runs from the child's `exit` handler (`engine-local.ts:322-323`); if VS Code itself is SIGKILLed the file survives. `_is_process_alive` then only asks "does *some* process have this PID", and PIDs are recycled — quickly on Linux under load.
- **Production impact:** the client connects to a port nothing is listening on, or (worse) to whatever now occupies it.
- **Introduced by the feature** (inherent to a PID-based liveness scheme). **Corrective direction:** cheap and decisive — after reading the file, attempt a short TCP connect to the advertised port before returning the hint; or record process start time alongside the PID.

### PR1874-F9 — `removeConnectionDiscovery` read-then-unlink is a TOCTOU against a concurrently starting engine — **P3**, confidence medium
- **File:line:** `apps/vscode/src/engine/local/engine-local.ts:468-476`. Between `readFileSync` and `unlinkSync`, a second VS Code window's engine can write its own entry, which is then deleted. The comment shows the author considered exactly this race and the guard narrows but does not close it.
- **Impact:** a live engine's entry disappears; discovery falls back to the cloud default. Self-healing on the next engine start. **Corrective direction:** accept and document, or use an atomic compare-and-delete (write to a pid-suffixed name and keep `connection.json` a pointer).

### PR1874-F10 — the advertised URI uses `localhost` while the engine binds `127.0.0.1`, against this file's own advice — **P3**, confidence high
- **File:line:** `engine-local.ts:453` writes `http://localhost:${this.actualPort}`, while `:150-157` passes `--host=127.0.0.1` with a comment warning: *"Bind an explicit address, never the name 'localhost'. Where it resolves to both ::1 and 127.0.0.1 …"*.
- On a host where `localhost` resolves to `::1` first, a consumer may attempt IPv6 and get a refused connection before falling back. The extension's own `emitStatus` already advertises `localhost` (`:167`), so this is **pre-existing** — but the discovery file propagates it to arbitrary third-party consumers who have none of that context.
- **Corrective direction:** advertise `http://127.0.0.1:${port}` — matching the bind address and this file's own reasoning.

### PR1874-F11 — the TypeScript half has no CI coverage at all — **P2** (process), confidence high
- **File:line:** `apps/vscode/scripts/tasks.js` exposes only `vscode:copy-readme`, `build-webview`, `compile-typescript`, `bundle-extension`, `stage-files`, `package-vsix`, `compile`, `build`, `clean` — **no `vscode:test`**. Nothing under `scripts/`, `.github/workflows/`, or `apps/vscode/package.json` runs `apps/vscode/src/test/*.test.ts`.
- The new `connectionDiscovery.test.ts` therefore never executes in CI; it is type-checked by `vscode:compile-typescript` and nothing more. **Pre-existing** (four other `src/test/*.test.ts` files in develop are equally unrun), but it means the writer half of this feature ships with **zero executed verification**.
- **Corrective direction:** out of scope for this PR — but the lead should know the "18/18 green" signal covers none of the TS code here. Worth a `vscode:test` action running `node --test` over the compiled output.

## 6. Compatibility and operational implications

- **Breaking for one configuration:** `RocketRideClient()` with neither `uri` nor `ROCKETRIDE_URI`, on a machine running the extension's local engine, now targets localhost instead of the cloud, with a credential drawn from the file (F5, F3). The PR's inline comment claims "nothing changes for anyone not relying on it" — that is not accurate for this case.
- **Not breaking otherwise:** explicit `uri`, explicit `auth`, `ROCKETRIDE_URI` and `ROCKETRIDE_APIKEY` all keep precedence (executed).
- **New failure mode with poor diagnostics:** when discovery yields a stale-but-live-looking entry (F8), the client reports an ordinary connection error against a port the user never chose. Nothing logs "URI came from the discovery file", which is exactly the breadcrumb needed. **A single `debug_message` naming the source of the URI would pay for itself.**
- **New file on disk** under the user's config dir, containing a credential field, world-readable by default (F2), removed on clean exit only.
- **Platform:** paths verified consistent on macOS by execution and on Windows/Linux by inspection; the liveness check is unsound on Windows (F4).
- **Cost per construction:** one `open()` + `json.load` + one `os.kill` syscall in `RocketRideClient.__init__` when no URI is configured. Negligible, but note it now happens on a code path that previously touched no I/O beyond `.env`.

## 8. Unresolved questions

1. **Windows `os.kill(pid, 0)`** (F4) — needs a Windows runner to settle. Everything else in this report is either executed or read directly from source.
2. **Is the credential fallback intended?** The PR title and docs describe *port* discovery; the code also does *credential* discovery. Was that reviewed as a deliberate decision?
3. **Should the fallback be opt-in?** A silent change of default target is a large behavioural surface for a convenience feature.
4. **Service and Docker backends** (`engine-service.ts`, `engine-docker.ts`) run on fixed ports and write nothing. Should discovery cover them, or is "local backend only" the intended scope? The docs do not say.
5. Does any consumer other than client-python plan to read this file (client-typescript, client-mcp, the CLI)? If so, the format deserves a versioned `schema` field before it ships.

---

## 9. Verdict

### **CHANGES REQUIRED**

The design is sound and unusually well-reasoned — the path contract is right, the readiness ordering is right, the best-effort discipline is real, and the scoping limitation is documented rather than hidden. Two things must change before merge, and one must be settled.

Exact remaining work:
1. **Constrain the discovered `uri` to loopback** in both `read_connection_discovery()` and `parseConnectionDiscovery()` (F1). Blocking.
2. **Stop adopting the file's `apiKey` as a credential** (F3), or gate the whole fallback behind an explicit opt-in (F1/F5). Blocking.
3. **Fix or guard `_is_process_alive` on Windows** (F4) — at minimum, skip the check when `sys.platform == 'win32'` rather than calling `os.kill`. Blocking until a Windows run says otherwise.
4. **Write the file with `mode: 0o600`** (F2), matching `service-mac.ts` / `service-linux.ts`.
5. **Update `packages/client-python/docs/index.md`** for the new URI/auth resolution order (F5) — `AGENTS.md` co-location rule.
6. Validate `pid > 0` and exclude `bool` (F7); advertise `127.0.0.1` rather than `localhost` (F10); add a `debug_message` naming the discovery file as the URI's source.
7. Add a test that constructs a real file at the real computed path (tmp-redirected) rather than `mock_open`, and — ideally — a cross-language path-equality test.

Not blocking: F8, F9, F11 (F11 is a repo-level gap the lead should carry separately).

> **Review comment — #1874**
>
> This is a well-scoped solution to a real annoyance, and the parts that are usually got wrong are got right here: the file is written only after uvicorn reports its port (so the advertised port is the bound port), removal is guarded on the writer's own pid, every read and write is best-effort, and the "last-connected, not a registry" limitation is stated in both the module docstring and `usage.md` rather than glossed over. I confirmed the cross-language path contract by running both sides on macOS — the TypeScript writer and the Python reader produce the identical string, `~/Library/Application Support/RocketRide/engine/connection.json`.
>
> Three blocking items, all on the reader side.
>
> **1. The file can redirect a caller's credential to an arbitrary host.** Neither parser constrains `uri`. With a real file on disk I get:
>
> ```
> file: {"uri": "https://attacker.example.com", "pid": <live>, ...}
> env:  ROCKETRIDE_APIKEY=sk-users-cloud-key
> → RocketRideClient()  uri='wss://attacker.example.com:5565/task/service'  apikey='sk-users-cloud-key'
> ```
>
> The write is same-user-only, which bounds this — but the path is fixed, well known, workspace-independent, and the file is written with default permissions (0644). Since this is by construction a *local engine* discovery hint, rejecting any non-loopback host in `read_connection_discovery()` (and mirroring it in `parseConnectionDiscovery`) costs nothing and closes it. Given the `apiKey` field, `mode: 0o600` would also match what `service-mac.ts:100` and `service-linux.ts:118` already do for credential-bearing files.
>
> **2. `client.py` adopts the file's `apiKey` as the credential.** With a valid file and no auth anywhere, `RocketRideClient()` comes back with `apikey='MYAPIKEY'` where it previously left `_apikey=None` and failed at connect with a clear message. The file's job is the port; I'd drop the key from both the writer and the fallback.
>
> **3. `_is_process_alive` does not port to Windows.** `os.kill(pid, 0)` is a POSIX idiom. On Windows CPython routes `os.kill` to `TerminateProcess(handle, sig)` for any signal that isn't `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` — so signal 0 asks to terminate, not to probe. And `ProcessLookupError` is POSIX-only: a missing PID on Windows raises a plain `OSError`, which `except OSError: return True` reads as *alive*, so the stale-entry protection the docs promise doesn't exist there either. The TypeScript side in this same PR gets it right (`process.kill(pid, 0)` at `engine-local.ts:231`, which Node documents as platform-independent). I'm on macOS and couldn't run this — could you check on a Windows runner? Guarding the call with `sys.platform == 'win32'` (treat as "can't tell" → alive) would be the safe minimum.
>
> Non-blocking, but worth folding in:
>
> - `packages/client-python/docs/index.md` still documents the URI as coming from `uri`/`ROCKETRIDE_URI` and says a `ValueError` is raised when both are empty. That's now a third source and a changed error path; per `AGENTS.md` the Python SDK doc should move with it. Related: `ROCKETRIDE_URI=''` used to raise `ValueError: Invalid URI '': missing hostname` and now silently resolves — worth a deliberate decision and a test, since CI is known to pass empty strings for the sibling variable.
> - Neither parser validates `pid`. `0`, `-1` and JSON `true` all pass (`isinstance(True, int)` is `True` in Python), and on POSIX `kill(0, 0)` / `kill(-1, 0)` both report "alive" — so a corrupt file defeats the staleness check. `pid > 0` and a `bool` exclusion would help. PID reuse after a VS Code crash has the same effect; a short TCP connect to the advertised port before returning the hint would settle both cheaply.
> - `engine-local.ts:453` advertises `http://localhost:${port}` while `:156` deliberately binds `--host=127.0.0.1`, with a comment right there explaining why `localhost` is a hazard when it resolves to `::1`. Advertising `127.0.0.1` would match the bind and the comment.
> - When the URI comes from the discovery file, nothing says so. One `debug_message` there would make "why is my client talking to localhost?" a one-line answer.
>
