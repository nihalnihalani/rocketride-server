## 2. Intended behaviour vs actual implementation

**Bug (issue #1841).** `send_files()` built one coroutine per file and handed the whole list to
`asyncio.gather()` (`data.py:720-726` on develop). A 500-file batch opened 500 pipes at once, and each
in-flight upload also holds an **open OS file handle** across every `await pipe.write(chunk)`
(`data.py:652`). Past the process fd limit the client drops the caller's own files; because
`upload_file()` catches per-file exceptions, they come back as `action: 'error'` entries rather than
as a raised exception, so a caller who does not inspect every result loses part of the upload
silently. `rocketride upload <directory>` is the documented way to reach that.

**Realistic trigger, measured (§5-A):** with the pipe replaced by a recording double, develop reaches
peak 120 pipes and peak 120 open file handles on a 120-file batch. The PR description's `ulimit -n 128`
run (112 of 300 files failing with `[Errno 24]`) is consistent with that; I did not re-run the ulimit
scenario, but the fd count that causes it is confirmed.

**Implementation.** `send_files(files, token, max_concurrent: int = 5)`. Validation
(`isinstance(max_concurrent, bool) or not isinstance(max_concurrent, int) or max_concurrent < 1` →
`ValueError`) runs at `data.py:559-563`, before the file list is even checked and before anything is
opened. The `gather` over N coroutines is replaced by a **fixed worker pool**
(`data.py:735-782`): `worker_count = min(max_concurrent, len(normalized_files))` workers pull from a
shared `next_index` cursor, read-and-increment with no `await` between them. Results are still
index-assigned into a pre-sized list, so input order holds. Each worker has its own
`except Exception` that records an `error` entry for the offending index so a raise cannot strand the
queue behind it. After `gather(..., return_exceptions=True)`, any outcome that is a `BaseException`
but not an `Exception` (i.e. `CancelledError`) is re-raised rather than returned as holes.

CLI: `--max-concurrent` added to the upload parser (`cli/main.py:415-425`, `type=int`, default 5,
`dest='max_concurrent'`); `< 1` rejected in `_validate_args` before a pipeline is started
(`cli/main.py:576-587`); `UploadCommand` forwards it defensively with
`getattr(self.args, 'max_concurrent', 5)` (`cli/commands/upload.py:275-277`).

Docs: the three reference tables gain `max_concurrent`; the agent doc's upload section is rewritten to
say `--max-concurrent` controls upload fan-out while `--threads` is the pipeline thread count, and the
stale `--pipeline` flag in the example is corrected to `--pipeline_path` (verified: the real flag is
`--pipeline_path`, `cli/main.py:402`).

### P2

**PR2004-F2 — the worker's recovery handler can overwrite a *successful* result with a fabricated failure.** (confidence: high — reproduced)

* `packages/client-python/src/rocketride/mixins/data.py:753-764` — the worker's `except Exception`
  writes `results[index] = {'action': 'error', 'bytes_sent': 0, 'file_size': 0, 'upload_time': 0.0,
  'result': None, 'error': str(e)}` unconditionally, without checking whether `upload_file()` had
  already filled that slot.
* `upload_file()` assigns `results[index] = event_body` at `data.py:723` and then calls
  `self.debug_message(...)` at `:729/:731`. `debug_message` invokes the caller's `on_debug_message`
  callback **unguarded** (`mixins/events.py:111-112`, over `core/dap_base.py:309-311`), so a raising
  user callback propagates out of `upload_file` *after* the correct result was recorded.
* Expected: a file that uploaded successfully is reported as `complete` with its real `bytes_sent`.
  Actual: it is reported as `error` with `bytes_sent: 0` and `file_size: 0`.
* Measured (§5-D):

  | tree | actions | bytes_sent |
  |---|---|---|
  | develop | `['complete'] * 4` | `[64, 64, 64, 64]` |
  | #1895 | `['complete'] * 4` | `[64, 64, 64, 64]` |
  | **#2004** | `['error'] * 4` | `[0, 0, 0, 0]` |

* Production impact: a caller that retries anything marked `error` re-uploads files that already
  landed, producing duplicate documents in the pipeline. Narrow trigger (needs a user
  `on_debug_message` that raises), but the failure is silent and the data consequence is duplication,
  not just a wrong label.
* Introduced by this PR — it is a direct consequence of adding a worker-level guard. develop and
  #1895 do not have it.
* Smallest corrective direction: `if results[index] is None:` before the assignment in the handler.
* Regression-test criterion: a test where `debug_message` raises on the per-file completion line and
  the successful entries still read `complete` with the real byte count.

**PR2004-F3 — the `file_size` TOCTOU is mitigated rather than removed, and the mitigation reports a completed upload as failed.** (confidence: high — reproduced)

* `packages/client-python/src/rocketride/mixins/data.py:710` keeps develop's
  `'file_size': os.path.getsize(filepath) if os.path.exists(filepath) else 0`. The `exists()` →
  `getsize()` window is a genuine race: a file deleted in between raises `FileNotFoundError` out of
  `upload_file`'s tail (outside its own try/except).
* Under develop this leaves a `None` hole in `results` (§5-A, case E: `None_holes=[2]`). #2004's
  worker guard converts it into an `error` entry, which is better than a hole — but the upload had
  already *completed*: the bytes were written and `pipe.close()` returned a real result. The caller is
  told a successful upload failed, which is F2's duplication risk again by a different route.
* Measured (§5-A, case E): develop `entry2=None`; **#2004 `entry2=error`**; #1895 `entry2=complete`.
* Pre-existing race, **worsened in reporting** by this PR (a `None` hole is at least obviously
  anomalous; a fabricated `error` is not).
* Smallest corrective direction: capture `file_size` once inside the try (what #1895 does at
  `data.py:637/712`) so the tail cannot re-stat, and keep the worker guard for genuinely unexpected
  failures.

**PR2004-F4 — the fix contradicts the maintainer's stated preference on this exact issue.** (confidence: high)

* On PR #1895 (the other fix for #1841), joshuadarron's CHANGES_REQUESTED review of 2026-08-08 was
  written against a revision that used a hand-rolled worker pool. Item 8, *"Non-blocking"*:
  > *"`asyncio.Semaphore` does this in four lines … That is ~20 lines lighter, keeps the diff to the
  > part that actually changed … The hand-rolled pool is correct, but it makes every future maintainer
  > re-derive why two workers cannot claim the same index."*
* #1895 complied and now uses a semaphore. #2004 (opened 2026-08-16, eight days later) is the
  worker-pool shape.
* This is a maintainability judgement, not a defect — and the reviewer himself marked it non-blocking
  and explicitly agreed the pool is correct. I raise it as P2 only because it is a *known* maintainer
  position on this issue that the PR does not acknowledge, so it will surface in review regardless.
* Note in #2004's favour on the same review: item 3 objected to a version that had dropped
  `return_exceptions=True` from `gather`. **#2004 keeps it** (`data.py:769-771`), so that specific
  defect is not present here.

### P3

**PR2004-F5 — only the first non-`Exception` outcome is re-raised; the rest are dropped.** (confidence: high)

* `data.py:778-780`: the loop `raise`s on the first `BaseException`-but-not-`Exception` outcome. Any
  further cancelled workers are discarded without chaining (`__context__`/`ExceptionGroup`). With
  `max_concurrent=1` this is moot; with several it can hide a second, different `BaseException`.
  Cosmetic for the realistic case (all outcomes are the same `CancelledError`).

**PR2004-F6 — the CLI rejects a bad `--max-concurrent` later and less idiomatically than argparse can.** (confidence: high)

* `cli/main.py:419` uses `type=int`, so `0` and `-1` pass parsing and are caught at
  `cli/main.py:585-587` with `print(...)` + `return 1`. Non-numeric values are rejected by argparse
  with `invalid int value: 'five'` (exit 2).
* The result is two different error surfaces and two exit codes for the same class of mistake, and any
  entry point that calls `parse_args()` without going through `_validate_args` (tests, embedding)
  accepts `0`. #1895's `type=positive_int` (`cli/main.py:79-87`) handles all four cases at parse time
  with one message and exit 2. Measured in §5-F.
* Not a defect on its own — the user does get a clear error before any pipeline is started, which was
  the requirement.

**PR2004-F7 — the CLI validation restructure is behaviour-neutral but widens the branch.** (confidence: high)

* `cli/main.py:576` changes `elif self.args.command == 'upload' and not ... and not ...:` into
  `elif self.args.command == 'upload':` with the two checks nested. I checked the whole `elif` chain
  (`cli/main.py:545-584` on develop): there is no `else`, and no later branch tests `'upload'`, so an
  `upload` invocation that previously fell through now stops at this branch with identical effect.
  Verified, not assumed — recording it because it is the kind of restructure that silently changes an
  `elif` chain.

Reading of the numbers:

* **The bound holds and it bounds both resources.** Peak pipes and peak open fds both track
  `max_concurrent` exactly, independent of list length. That is the fix #1841 asked for.
* **#2004 additionally bounds pending work.** Peak live asyncio tasks is `min(limit, n) + 1` regardless
  of `n`, where develop and #1895 create one task per file (121 tasks for 120 files). For a
  million-file batch that is the difference between `max_concurrent` task objects and a million.
  `normalized_files` and `results` are still O(n) in both, and normalisation still stats every file up
  front, so this bounds scheduler objects, not total memory.
* **Per-invocation, not per-client (both PRs).** Case I: two concurrent `send_files()` calls on the
  same client each get their own limit of 5, so a client can still have 10 pipes in flight. The bound
  is per call by construction (the pool/semaphore is created inside `send_files`). Worth documenting;
  neither PR does.
* The failed pipe is deliberately not finalised (12 opened / 11 closed) on all three trees — that is
  develop's behaviour, unchanged. #1895 adds a comment explaining why; #2004 does not.

## 6. Compatibility + operational implications

* **Signature-compatible:** `max_concurrent` is the third positional-or-keyword parameter with a
  default; every existing `send_files(files, token)` call keeps working. In-repo callers checked:
  `cli/commands/upload.py` (updated) and `packages/ai/src/ai/modules/mcp/engine.py:45`, whose
  `EngineClient` protocol declares `send_files(self, files, token) -> Any` — still satisfied.
* **Behaviour change, correctly identified as the point of the issue:** callers relying on unbounded
  parallelism now get 5 at a time. On a large directory, wall-clock time can increase by roughly the
  ratio of the old effective parallelism to 5, because each slot waits on `pipe.close()`, which blocks
  on server-side processing. The PR body does not quantify this; joshuadarron raised exactly this
  point on #1895 (item 5). Worth a release-note line.
* **Return annotation corrected** from `-> UPLOAD_RESULT` to `-> List[UPLOAD_RESULT]`
  (`data.py:490`). This is a real pre-existing bug: the method has always returned a list, and the
  reference docs always said `List[UPLOAD_RESULT]`. Type-checked consumers were being lied to.
* **Docstring `Raises:` corrected**: `FileNotFoundError` removed (never raised —
  `data.py:596` raises `ValueError(f'File not found: {filepath}')`), missing paths folded into the
  `ValueError` line.
* **Doc bug fixed in passing:** `docs/agents/ROCKETRIDE_python_API.md:159` had `--pipeline`; the real
  flag is `--pipeline_path` (`cli/main.py:402`). Verified.
* No new dependency; no change to the wire protocol or to `UPLOAD_RESULT`'s shape.

## 8. Unresolved questions

1. Semaphore or worker pool? joshuadarron asked #1895 for the semaphore (non-blocking). If that
   preference stands, #2004's core mechanism is the thing being objected to — which matters for the
   keeper decision, not for correctness.
2. Should the bound be per call (current, both PRs) or per client? A per-client bound is what actually
   protects a shared connection; per-call means N concurrent `send_files()` calls give N×limit pipes.
   Neither PR documents which it is.
3. Is 5 the right default given the throughput cost on large directories, and does it need a
   release-note entry?

## 9. Verdict — **CHANGES REQUIRED**

The diagnosis is right, the bound is real and correctly measured (peak pipes *and* peak fds track
`max_concurrent` exactly, independent of list length), input order is preserved, validation runs
before anything is opened, cancellation propagates, and the branch fixes two genuine pre-existing bugs
(the return annotation and the `FileNotFoundError` docstring) plus a stale CLI flag in the docs. The
worker pool is the only shape here that also bounds *pending* work, which is a real advantage over a
semaphore for very large batches. The 31 tests are unusually thorough and mutation-informed.

Blocking work:

3. Capture `file_size` once inside the try so the tail cannot re-stat, instead of relying on the
