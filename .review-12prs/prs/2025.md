## 2. Intended contract vs actual

**Intended (reconstructed and CONFIRMED).** `packages/client-typescript/package.json` declares `exports["./app-sdk"]` and `docs/README-apps.md` documents `import … from 'rocketride/app-sdk'` (lines 122–234, 314, 744, 1043, 1103–1110), but the base `tsconfig.json` sets `include: ["./src/client/**/*"]` with **no explicit `rootDir`**, so `src/app-sdk/` was never compiled and `dist/*/app-sdk/` never existed. Adding `src/app-sdk` to the include list moves TypeScript's *inferred* `rootDir` from `./src/client` to `./src`, which shifts every `src/client/*` output one level deeper — hence the `package.json` path rewrites.

Both halves of that reasoning are **empirically verified** (§5). The pre-existing precedent is `tsconfig.cli.json`, which already includes two `src/` subtrees and whose `bin` path is correspondingly doubled (`./dist/cli/cli/rocketride.js`).

**Actual.** The fix works: after the change, all three declared entry points resolve from a clean consumer outside workspace resolution, in both CJS and ESM. But the output-path move breaks one in-repo consumer that hard-codes the old path (PR2025-F1), which is the proven cause of all 5 failing checks at head.

### PR2025-F1 — P1 · confidence HIGH · **introduced by this PR** · proven root cause of all 5 failing checks
**Where:** `packages/shell/scripts/pack-shell.js:179` (file **not** touched by this PR; present identically at the PR head and at develop)
```js

```
**Trigger:** any `./builder shell:build` / `pack-shell` after `client-typescript:build`.
**Expected vs actual:** the guard should confirm the SDK was built; instead it checks a path this PR relocates to `dist/types/client/index.d.ts`, so it throws *even though the build fully succeeded*.
**Production impact:** `shell:build` — and therefore the whole platform build on every OS — fails permanently, not transiently. The shell tarball (`shell.tgz`, which vendors the SDK via `bundleDependencies`) can never be produced.
**Evidence:** In CI run `32079323156` at this exact head, the builder log shows `client-typescript:compile-cjs`, `compile-esm`, `generate-types`, `compile-cli`, `post-build`, `create-package`, `sync`, `docs-generate` all **STARTED with no `[FAILED]`**, and the *only* `[FAILED]` line in the entire log is `pack-shell: packages/client-typescript/dist is missing`. **Attribution of the 5 failing checks:** `Build / Ubuntu 22.04`, `Build / macOS (ARM64)`, `Build / Windows Server 2022`, `check-externals (PR)` all fail on this identical `pack-shell` error; `CI OK` is the aggregate gate. **All 5 are PR-caused — none are stale-base or flake.**
**Introduced/worsened/pre-existing:** introduced.
**Smallest corrective direction:** one line — `path.join(sdkRoot, 'dist', 'types', 'client', 'index.d.ts')`. Note `vendorSdkInto()` at `pack-shell.js:100` does a recursive `fs.cpSync` of the whole `dist/`, so nothing else in that script needs changing.
**Regression-test criterion:** a test that reads `package.json` and asserts each of `main`, `module`, `types` and every `exports[*].{types,import,require}` **exists on disk** after a build — i.e. assert against *artifacts*, not against config strings. The PR's own `build-config.test.ts` asserts only config strings and therefore cannot catch this class of break (see PR2025-F6).

### PR2025-F3 — P2 · confidence HIGH · newly reachable (the underlying `import` is pre-existing; this PR is what ships it)
**Where:** `packages/client-typescript/src/app-sdk/types.ts:35` → emitted to `dist/types/app-sdk/types.d.ts:1`
```ts
import type * as React from 'react';
```
`packages/client-typescript/package.json` declares **no** react dependency — not `dependencies`, `peerDependencies`, `optionalDependencies`, nor `devDependencies`. It compiles in-repo only because the **root** `package.json:46` has `@types/react` as a devDependency that Node/TS directory-walking finds — a textbook case of workspace hoisting hiding a missing package dependency (exactly the risk this review was asked to probe).
**Trigger:** any consumer of `rocketride/app-sdk` without react types installed.
**Consumer impact (measured, §5 rows 14–15):** with `skipLibCheck: false` a clean consumer gets `TS2307: Cannot find module 'react'` (`types.d.ts:1`) and `TS2503: Cannot find namespace 'React'` (`index.d.ts:138`). Installing `@types/react` reduces those to **zero**. With the common `skipLibCheck: true` the errors are suppressed but the React-typed members degrade silently.
Contrast: `sequelize` has the same shape of dependency and *is* correctly declared as an optional `peerDependency`.
**Corrective direction:** add `react` (and/or `@types/react`) as an **optional `peerDependency`** mirroring the existing `sequelize` entry, and add `@types/react` to the package's own `devDependencies` so the build does not rely on root hoisting.
**Regression-test criterion:** type-check a fixture consumer of `rocketride/app-sdk` with `skipLibCheck: false` and no react installed; it must either pass or fail with a *declared* peer-dependency warning.

### PR2025-F4 — P2 · confidence HIGH · pre-existing design limitation, **not fixed** by this PR
`moduleResolution: "node"` (node10 — still TypeScript's default for `module: commonjs`) ignores `exports`, so `rocketride/app-sdk` is unresolvable there. Measured: `TS2307 … There are types at '…/dist/types/app-sdk/index.d.ts', but this result could not be resolved under your current 'moduleResolution' setting.` `node16` and `bundler` both pass. Worth flagging because the SDK's own `packages/client-typescript/tsconfig.json` uses `moduleResolution: "node"`, so the monorepo itself cannot consume its own subpath export.
**Corrective direction (optional, not a merge blocker):** add a `typesVersions` fallback, or state the required `moduleResolution` in `docs/README-apps.md`.

### PR2025-F5 — P2 · confidence HIGH · pre-existing design, newly *reachable* because of this PR
`dist/esm/app-sdk/index.js` is literally `export {};` (and the CJS twin exports nothing) while `src/app-sdk/index.ts` declares 13 **value** exports via `export declare` (`useShellConnection`, `useShellApiConfig`, `useWorkspace`, `useAuthUser`, `useLogout`, `useSubscriptions`, `Documents`, `connectionManager`, `getDebugLog`, `clearDebugLog`, `onAny`, `useAppComponent`, `getClient`). Measured: `import { connectionManager } from 'rocketride/app-sdk'` in native ESM throws `SyntaxError: The requested module 'rocketride/app-sdk' does not provide an export named 'connectionManager'`; in CJS the binding is silently `undefined`.
This is intentional — `src/app-sdk/index.ts:24-40` explains that Module Federation replaces the module at runtime, and `docs/README-apps.md:208` shows the required `shared` config. But before this PR the failure was a loud `MODULE_NOT_FOUND`; after it, the module resolves and is hollow, which is a worse failure mode for anyone outside an MF host. Docs at `README-apps.md:125/146/165` show value-import forms without an adjacent "requires Module Federation" warning.
**Corrective direction:** a one-line note in `docs/README-apps.md` next to the value-import examples. Not a merge blocker.

## 6. Compatibility / operational implications

- **Published-artifact change:** consumers importing via `main`/`module`/`types`/`exports` are unaffected — the paths move but the specifiers do not. Anyone deep-importing `rocketride/dist/types/index.d.ts` (as `packages/ai/.../apps/tsconfig.json` and `pack-shell.js` do) breaks. No deep-import path is a documented public API.
- **Version:** the tarball is still `1.3.0`. Publishing a package whose internal layout changed under an already-published version would be a footgun; `_release.yaml:211` guards with `npm view rocketride@$VERSION` and skips if present, so in practice this ships under a new version. Worth a release-note line either way.
- **Node/bundler support:** ESM + CJS both verified on Node 25. Subpath `exports` needs Node ≥ 12.7; the package declares no `engines` (root declares `node >= 20.0.0`).
- **TypeScript support:** `node16`/`nodenext`/`bundler` only for subpath imports (PR2025-F4); root import works under all three.
