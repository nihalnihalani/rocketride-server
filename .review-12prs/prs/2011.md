## 2. Intended behaviour vs actual implementation

**Intent (issue #1987).** A user on `https://api.rocketride.ai` calls `client.deploy.*` and gets
`RuntimeError: Invalid command: rrext_deploy_add`. The error names an internal RPC, so it reads as a
version mismatch rather than a capability gap. The issue asks for one of two outcomes: deployments
work on Cloud, **or** the SDK reports the gap directly — the issue's own words suggest a distinct
exception type (`NotSupportedError`) *"plus a sentence in the Cloud docs"*.

**Implementation.** `DeployApi._ensure_supported()` (`deploy.py:109-118`) reads
`self._client.get_connection_info()['uri']`, extracts the hostname, strips a trailing DNS dot, and
compares it for equality against `urlparse(CONST_DEFAULT_WEB_CLOUD).hostname` (`api.rocketride.ai`).
On a match it raises `RuntimeError('Deploy operations are not supported on RocketRide Cloud.')`.
The call is inserted at the top of all 16 public `DeployApi` methods, before any `self._client.call()`.

**Answer to the explicit question — usability restriction or security boundary?**
It is a **usability restriction only**, and must be described as such. Three independent proofs:

* It runs entirely client-side, from a value the caller controls (`uri`).
* `client.call('rrext_deploy', subcommand='publish', ...)` reaches the same server command with the
  guard untouched — `call()` is public and documented (`client.py:305`).
* The server is the actual authority: `cmd_deploy.py` performs the permission checks
  (`task.monitor` for reads, `task.control` for mutations) regardless of what the client believes.

## 4. Confirmed findings

### P1

**PR2011-F1 — the guard blocks a deploy API that this repo's server implements on SaaS; default-constructed clients lose `client.deploy` entirely.** (confidence: high on the code facts, medium on production Cloud behaviour — see caveat)

* `packages/client-python/src/rocketride/deploy.py:109-118` (the guard), plus the 16 call sites.
* Trigger: any `client.deploy.*` call from a client whose URI host is `api.rocketride.ai`. That
  includes **every default-constructed client**: `client.py:204` sets
  `uri = self._env.get('ROCKETRIDE_URI', CONST_DEFAULT_WEB_CLOUD)`, so `RocketRideClient(auth=...)`
  with no URI resolves to `wss://api.rocketride.ai/task/service` (measured, §5-C).
* Expected: deploy is refused only where it genuinely is not implemented.
  Actual: deploy is refused on the host this repo's own server code supports.
* Evidence that the premise is contradicted by the repo:
  * `packages/ai/src/ai/modules/task/task_conn.py:77,108,199` mixes `DeployCommands` into `TaskConn`
    **unconditionally** — there is no edition branch on the command registration.
  * `packages/ai/src/ai/account/deployment_backend.py:23-24` — the file backend is described as
    *"the OSS implementation of the account module's `deployments_*` interface, **and the artifact-file
    layer the SaaS implementation shares**"*.
  * `packages/ai/src/ai/account/base.py:465` — *"(cmd_deploy, the scheduler, UIs) never branch on
    edition."* SaaS overrides the storage backend, not the availability of the command.
  * The issue reports `rrext_deploy_add` / `rrext_deploy_list`. **Neither command name exists anywhere
    in this tree** — the current protocol is a single `rrext_deploy` dispatched by `subcommand`. That
    is the signature of SDK↔server version skew, not a permanent capability boundary.
* Production impact: shipping this turns a transient version-skew error into a permanent, client-side
  refusal that only a new SDK release can lift. Every Cloud user of `client.deploy` — including
  publish, promotion and **rollback**, which is the one call you want during an incident — is blocked.
* Introduced by this PR.
* Smallest corrective direction: replace the hardcoded host with the SDK's existing capability
  negotiation. `types/client.py:345-352` documents `ServerInfoResult.capabilities` as `['oss']` for
  open-source and `['saas']` for cloud, sourced from `AccountBase.capabilities`
  (`ai/account/base.py:53`, `ai/account/oss/__init__.py:66`) and reachable pre-auth via
  `get_server_info()` (`rrext_public_probe`); `ConnectResult.capabilities` carries the same tag
  post-auth. If the real gap is "this server build lacks the command", the honest guard is
  a capability/command probe, not a domain-name test. If Cloud genuinely will never support deploy,
  that decision needs to be recorded server-side (or in the capability list) and cited here — a
  maintainer confirmation is a prerequisite for merging any version of this change (§8, Q1).
* Regression-test criterion: a test that a client pointed at a server advertising deploy support
  can call `deploy.publish()` regardless of hostname, and one that a server not advertising it is
  refused regardless of hostname.

### P2

**PR2011-F3 — read-only and server-independent operations are blocked along with the mutations.** (confidence: high)

* `deploy.py:216` (`list`), `:233` (`get`), `:261` (`versions`), `:302` (`artifact`), `:338`
  (`history`), `:530` (`preview`).
* `preview()` is documented as *"THE single cron evaluator"* (`deploy.py:490-493`) — pure schedule
  validation with no deployment state involved. A UI that validates a cron expression through the SDK
  now fails on Cloud even though nothing about the call is deploy-specific.
* Blocking the five read operations also removes the only way for a Cloud user to *discover* that
  they have no deployments — `list()` returning an empty envelope is strictly more useful than an
  exception. Impact: a dashboard that calls `deploy.list()` on connect crashes rather than rendering
  an empty state.
* Introduced by this PR. Direction: if the guard survives at all, scope it to the operations that
  actually require the unsupported backend, and say in the message which ones are affected.

**PR2011-F4 — the exception is indistinguishable from a server-side failure, which is the specific complaint the issue raised.** (confidence: high)

* `deploy.py:116`. `RuntimeError` is exactly what `client.call()` raises when the server signals
  failure (`client.py:341: raise RuntimeError(response.get('message', ...))`), so it is *internally
  consistent* — but it means `except RuntimeError` around a deploy call cannot separate "Cloud does
  not do this" from "the server rejected your arguments" except by matching the message string.
  The issue asked for a distinguishable type (`NotSupportedError(...)`).
* The SDK already has a hierarchy to extend — `core/exceptions.py` exports `RocketRideException`,
  `ConnectionException`, `AuthenticationException`, `PipeException`, `ExecutionException`,
  `ValidationException`. None is used here, and the new failure mode is not documented in any
  `DeployApi` method's `Raises:` section (all 16 docstrings are unchanged).
* Direction: add a narrow exception type (subclassing both `RocketRideException` and `RuntimeError`
  keeps existing `except RuntimeError` handlers working), export it, and document it on the methods.

**PR2011-F5 — the docs half of the linked issue is not done.** (confidence: high)

* The issue asks for the capability check *"plus a sentence in the Cloud docs"*.
  `packages/client-python/docs/index.md:70` still advertises *"Deployments — Persist pipelines
  server-side and run them on a cron schedule via `client.deploy`"* with no host caveat, and the
  `client.deploy` API table at `:347-370` is untouched. No doc file is in the diff.
* Impact: the SDK reference still promises a feature the SDK now refuses, for the majority of users.

### P3

**PR2011-F6 — host matching is inconsistent with the SDK's own idea of "cloud", and is trivially side-stepped.** (confidence: high)

* `deploy.py:111-114` matches `hostname == 'api.rocketride.ai'` exactly, while
  `mixins/connection.py:387` treats **any** host containing `rocketride.ai` as cloud (it is the
  condition for not appending a default port). Measured (§5-C): `eu.api.rocketride.ai` and
  `cloud.rocketride.ai` are *allowed* by the guard but *treated as cloud* by URI normalisation.
  A proxy or private DNS alias in front of Cloud is likewise allowed.
* This is a correctness wart rather than a hole, precisely because the guard is not a security
  boundary (see §2) — but it means the guard silently does nothing for a subset of real Cloud users,
  who then get back the confusing `Invalid command` error the PR set out to remove.

**PR2011-F7 — the new tests do not cover the negative direction they claim to.** (confidence: high)

* `tests/test_deploy_unit.py` has one self-hosted case (`ws://localhost:5565`) and it only exercises
  `publish`. The 16-method parametrised test covers the *rejected* direction only. There is no test
  that a self-hosted client can reach `list`/`get`/`preview`/etc., so a future over-broad guard
  would not be caught.
* `FakeClient` returns `{}` from `call()`, so nothing checks that the guarded methods still forward
  the right `subcommand` on the allowed path (except `publish`).

## 6. Compatibility + operational implications

* **Behaviour change, unflagged.** Six methods that previously returned data on Cloud now raise. The
  PR body describes this as adding "a clear RuntimeError before unsupported commands are sent"; it
  does not state that the default-configured client is affected. Nothing in `CHANGELOG.md` or the
  docs records it.
* **Rollout/rollback.** The block is compiled into the SDK. If Cloud ships (or has already shipped)
  `rrext_deploy`, every pinned SDK version carrying this patch stays broken until users upgrade.
  A capability probe degrades on its own; a hostname literal does not.
* **Same-build blast radius.** `packages/client-python/src/rocketride` is synced into the engine
  (`packages/client-python/scripts/tasks.js`, `makeSyncClientPythonAction` → `dist/server/rocketride`),
  and server modules import from it. No in-repo consumer uses `DeployApi` today
  (`git grep` for `\.deploy\.` under `packages/ai` finds only the unrelated `rrext_app_deploy` path),
  so the runtime blast radius is limited to external SDK users — unlike #2007.
* No public signature changed; no new dependency (`urllib.parse` is stdlib).

## 8. Unresolved questions

1. **(blocking)** Does RocketRide Cloud serve `rrext_deploy` today? The repo says the command is
   registered unconditionally and the SaaS deployment backend shares the OSS artifact layer. If Cloud
   *does* serve it, this PR should be closed in favour of a version-skew fix. Needs a maintainer.
2. If Cloud deliberately does not offer deployments, why is that not expressed in the
   `capabilities` tag the server already sends? Answering this decides the shape of the fix.
3. Is a capability/feature probe (`get_server_info().capabilities`, or a `commands` list) acceptable
   as the detection mechanism, given it costs one pre-auth round trip?
4. Should read-only operations (`list`, `get`, `versions`, `artifact`, `history`) and `preview` be
   exempt (F3)?

## 9. Verdict — **CHANGES REQUIRED**

The failure mode the issue describes is real and worth fixing, the guard is correctly placed before
any network side effect, and the tests are honest about what they cover. But the detection mechanism
contradicts the repository's own server code and its existing capability negotiation, the change
silently disables `client.deploy` for every default-constructed client, and CI is red on formatting.

Remaining work, in order:

1. Resolve §8 Q1 with a maintainer. If Cloud supports deploy, close this PR.
2. If the gap is real: detect it from `ServerInfoResult.capabilities` / `ConnectResult.capabilities`
   (or a command probe) instead of a hostname literal. (F1)
3. Run `ruff format` on both files. (F2)
4. Narrow the guard to operations that actually need the backend; leave `preview` alone. (F3)
5. Introduce a distinguishable exception type deriving from both `RocketRideException` and
   `RuntimeError`; document it in the 16 `Raises:` sections. (F4)
6. Add the doc sentence the issue asked for, in `packages/client-python/docs/index.md`. (F5)
7. Add positive-direction tests for a supported deployment across all 16 methods. (F7)
