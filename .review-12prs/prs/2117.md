## 2. Intended contract vs. actual

**Stated intent (commit body):** a just-registered pipeline's per-pipe data listener can still be binding when `open()` reaches it; under load this surfaces as a transient `[Errno 111] Connect call failed` that is indistinguishable from a real "pipeline isn't running" failure. Retry a few times with short backoff; everything else fails fast.

**What the code actually does** (`packages/client-python/src/rocketride/mixins/data.py:185-217` @ head):

```python
response = None
for attempt in range(1, _PIPE_OPEN_RETRY_ATTEMPTS + 1):
    request = self._client.build_request('rrext_process', arguments={'subcommand': 'open', ...}, token=self._token)
    response = await self._client.request(request)
    if not self._client.did_fail(response):
        break
    message = response.get('message') or ''
    if attempt < _PIPE_OPEN_RETRY_ATTEMPTS and _is_transient_pipe_open_error(message):
        await asyncio.sleep(_PIPE_OPEN_RETRY_BACKOFF_SECONDS * attempt)
        continue
    ... raise PipeException(response)
```

- **Operation retried:** the whole `rrext_process`/`open` **DAP round trip**, not a socket connect. The client never connects to the failing port itself.
- **Error types covered:** substring match on the DAP response `message` for `'Connect call failed'` **or** `'Connection refused'` (`mixins/data.py:71-72`). Nothing else. Auth failures, invalid tokens, wrong MIME type, terminated pipelines, "no pipeline found" all raise on attempt 1 — verified by execution (§5, E1/E3).
- **Attempt limit / delay:** 3 attempts; sleeps `0.25 * attempt` between them → 0.25 s then 0.50 s; **client-side budget 0.75 s**, no jitter, no other cap.
- `asyncio` is already imported at `mixins/data.py:54` on both sides — no new import needed.
- The loop cannot fall through: on the last attempt the `attempt < N` guard is false, so it always breaks or raises; `response` is never `None` at the post-loop `response.get('body', {})`.

**Where the failure actually originates** (traced end-to-end; this materially changes how the PR should be judged):

1. SDK sends `rrext_process`/`open` — `packages/client-python/src/rocketride/mixins/data.py:173-183`.
2. Engine handles it — `packages/ai/src/ai/modules/task/commands/cmd_data.py:94` → `:139 wait_for_running()` → `:144 task._send_data(request)`.
3. **`packages/ai/src/ai/modules/task/task_engine.py:748-769`** builds `ws://127.0.0.1:{self._data_port}/task/data` and connects to the task subprocess. That connect is what gets refused.
4. `packages/client-python/src/rocketride/core/transport_websocket.py:378` (`websockets.connect`) raises; re-raised verbatim at `:411` as `ConnectionError(f'{e}')`, so CPython's `"…Connect call failed ('127.0.0.1', 40006)"` survives byte-for-byte into the DAP error `message` (`core/dap_base.py:214` → `:756`).

So the failing hop is **engine → task subprocess**, not client → engine. The client-side retry re-drives that engine-side connect. Coherent — but see PR2117-F1.

## 4. Findings

### PR2117-F1 — develop already retries this exact connect, 10× at the connect site; the PR adds a second outer loop whose real cost is ~10× its stated one — **P1**, confidence high
- **File:line:** `packages/ai/src/ai/modules/task/task_engine.py:748-769` (develop @ `973cd9b4`, and identical at merge-base `b1b45b855`).
- The engine wraps `_connect_data_client()` in `@retry(stop=stop_after_attempt(10), wait=wait_fixed(0.15), reraise=True, before_sleep=…debug_message…)`, with a comment naming the very race #2117 describes: *"the C++ engine emits the `>SVC*1` readiness signal slightly before the child process's uvicorn server has finished binding to its port … We retry up to 10 times (150ms apart)."* `git log -S 'stop_after_attempt(10)'` dates it to `81977440` ("chore: initial commit", 2026-02-20) — long before this PR.
- **Trigger:** any pipeline whose data listener is not accepting yet.
- **Expected vs actual:** the PR's model is "one refused connect → wait 0.25 s → try again". Actual: the error reaching `open()` is already a **≈1.35 s exhausted** retry. Because `self._data_client` stays `None` after failure, each client attempt re-enters `_send_data` and re-runs the full 10 × 0.15 s loop. Worst-case `open()` latency goes from ≈1.35 s to **≈3 × 1.35 + 0.75 ≈ 4.8 s**, not "a few short attempts". The 0.25/0.50 s backoff is a rounding error next to the per-attempt server cost.
- **Production impact:** every caller of `send()` / `send_files()` / `client.pipe(...)` inherits a ~3.5× longer worst-case stall against a pipeline that will never become ready. Callers with their own timeouts may now time out where they previously got a fast, clear error.
- **Evidence:** E11, E12 (git), plus the source at `task_engine.py:751-757`. The 4.8 s figure is arithmetic over verified constants, not measured (the engine cannot run here).
- **Introduced.** Not redundant — it does extend the budget ~3.5× — but **mis-specified**: it is documented as a small client-side retry when it is a multiplier on an existing server-side retry, applied at a layer that cannot see how much waiting already happened.
- **Corrective direction:** either (a) raise `stop_after_attempt` / add jitter at `task_engine.py:751`, where the connect and its context live, and drop the SDK loop; or (b) keep the SDK loop, reduce attempts to 2 so worst case stays under ~3 s, and state the real bound in the docstring and `packages/client-python/docs/index.md`.
- **Regression-test criterion:** a test asserting the documented worst-case wall-clock bound of `open()` against a server that never becomes ready.

### PR2117-F2 — a merge that takes "theirs" silently reverts #2127's message/hint split — **P1**, confidence high (reproduced)
- **File:line:** the conflict hunk in `packages/client-python/src/rocketride/mixins/data.py` (PR side `:207-216`; develop side introduced by `4e6e56cd`, PR #2127).
- develop moved the "Common causes" developer checklist **out of** the user-visible `message` and into `PipeException.hint`, precisely so applications can show `message` to end users. The PR branch predates that and still does `msg = f'{msg}\n\n' + checklist; response['message'] = msg`.
- **Expected vs actual (reproduced, E5/E4):** PR head → `PipeException: "TCP connection failed: [Errno 61] Connect call failed ('127.0.0.1', 54093)\n\nCommon causes:\n- Pipeline isn't running…"`. develop → `PipeException: "TCP connection failed: [Errno 61] Connect call failed ('127.0.0.1', 40006)"` with the checklist in `hint`.
- **Production impact:** a developer checklist leaks back into end-user-facing text; `hint` becomes unset for this failure; #2127's `mimetype=` → `mime_type=` typo fix is reverted too (the PR branch still carries the old spelling).
- **Introduced by the rebase**, not by the author's code — but it is exactly the failure mode a mechanical conflict resolution produces.
- **Corrective direction:** resolve by keeping develop's `response = dict(response); response['message'] = …; response['hint'] = …; raise PipeException(response)` and wrapping only the request + `did_fail` check in the loop (concrete resolution in §7).
- **Regression-test criterion:** `packages/client-python/tests/test_task_error_codes.py` must still pass post-rebase, plus one test asserting `PipeException.hint` is set and `message` carries no checklist.

### PR2117-F3 — the predicate matches permanent failures from remote nodes — **P2**, confidence medium-high
- **File:line:** `packages/client-python/src/rocketride/mixins/data.py:71-72`.
- `'Connection refused'` is not unique to the engine→subprocess hop. `nodes/src/nodes/remote/client/IInstance.py:39` (`beginInstance`) does a blocking `websockets.sync.client.connect(self.IGlobal.urlProcess…)` to a **configured** host/port (`nodes/src/nodes/remote/client/IGlobal.py:46,68`). `beginInstance` runs inside the pipe-instance build that `data_conn._open()` drives (`packages/ai/src/ai/modules/data/data_conn.py:572,580`).
- **Trigger:** a `remote` node configured with a dead host/port.
- **Expected vs actual:** should fail fast with a clear diagnosis; instead `open()` retries 3× (≈4.8 s per F1), then reports the same error.
- **Production impact:** delayed diagnosis of a static misconfiguration, and 3× the connection attempts against whatever *is* at that address.
- **Introduced.**
- **Corrective direction:** narrow the predicate. Best: key on a machine-readable `code` — #2127 already added the mechanism (`DAPBase.build_exception` copies `code` onto the DAP error packet) and its own commit message argues that applications should not match on prose *"that a reword or a translation would silently break"*. A data-channel-specific code (e.g. `DATA_CHANNEL_UNAVAILABLE`) emitted at `task_engine.py:769` would make this exact.
- **Regression-test criterion:** a `Connection refused` message originating outside the data channel is not retried.

### PR2117-F4 — a disconnect during the backoff window replaces the real error with `RuntimeError('Server is not connected')` — **P3**, confidence high (reproduced)
- **File:line:** `packages/client-python/src/rocketride/core/dap_client.py:214-215`, reached from the retried `self._client.request(...)` at `mixins/data.py:196`.
- **Trigger:** the WebSocket to the engine drops during the 0.25 s / 0.50 s sleep.
- **Expected vs actual (E8/E9):** PR head → `RuntimeError: 'Server is not connected'` after 0.251 s; develop → `PipeException: "TCP connection failed: [Errno 61] Connect call failed…"` after 0.000 s. The server's diagnosis is discarded and replaced by a generic transport error, and the exception type changes from `PipeException` to `RuntimeError` — a cause the `open()` docstring's `Raises:` block does not mention.
- **Worsened** (a disconnected transport could always raise this on attempt 1; the PR opens a new ~0.75 s window in which it can happen *after* a real server error was already in hand).
- **Corrective direction:** wrap the retried `request()` so a transport failure on attempts ≥ 2 re-raises the last server `PipeException` (or chains via `raise … from`), and update the docstring's `Raises:`.
- **Regression-test criterion:** disconnect-during-backoff must surface the last server message.

### PR2117-F5 — the retry is silent: no debug message, no attempt counter — **P3**, confidence high
- **File:line:** `packages/client-python/src/rocketride/mixins/data.py:198-200`.
- `DAPBase.debug_message` is available on `self._client`, and the engine's equivalent retry uses `before_sleep=…debug_message…` (`task_engine.py:756`). Here, up to ~4.8 s of waiting produces no trace; an operator sees only "`open()` was slow".
- **Introduced.** **Corrective direction:** one `self._client.debug_message(f'pipe open attempt {attempt} failed ({message}); retrying in {delay}s')` per retry.

### PR2117-F6 — no jitter; `send_files()` fan-out retries in lockstep — **P3**, confidence medium
- **File:line:** `mixins/data.py:199` with `send_files()` at `mixins/data.py:639`.
- The scenario the PR cites is "many pipelines opened at once". All concurrent `open()` calls that fail together retry at exactly +0.25 s and +0.75 s, against a server-side `asyncio.Semaphore(threadCount)` (`packages/ai/src/ai/modules/data/data_conn.py:189-201, 554-558`). Fixed backoff maximizes collision. **Corrective direction:** add jitter.

### PR2117-F7 — retry safety / idempotency: **clean** (no defect)
- Verified: when the engine's connect fails, `_open()` is never reached — the failure is raised inside `task._send_data` before `on_rrext_process` dispatches (`packages/ai/src/ai/modules/task/commands/cmd_data.py:144`). No pipe is allocated, no semaphore slot held. Even when `_open()` itself throws later, `packages/ai/src/ai/modules/data/data_conn.py:611-619` returns the pipe via `putPipe` and `:627-631` releases the semaphore.
- **The retried operation is idempotent for the failure mode being retried.** This is the strongest part of the PR and it holds.

### PR2117-F8 — pre-existing: concurrent `open()` on one `DataPipe` can double-allocate; the PR widens the window — **P3**, confidence high
- **File:line:** `mixins/data.py:183` (`if self._opened: raise`) vs `:219-220` (`self._opened = True`). `_opened` is set only after the request completes, so two concurrent `open()` calls on the same pipe object both pass the guard, both allocate a server pipe, and only the last `_pipe_id` is retained — the other leaks a semaphore slot until the zombie monitor reaps it (`data_conn.py:430-441`). Identical on develop; the retry loop widens the window by up to 0.75 s. **Pre-existing / worsened.** Out of scope here; worth its own issue.

### PR2117-F9 — cross-SDK divergence — **P3**, confidence high
- `packages/client-typescript/src/client/client.ts:133-156` has no equivalent retry. After this merges, the same pipeline race is transparent in Python and fatal in TypeScript. Not a defect in this PR; a merge-plan consideration (§9).

### Suggestions / questions (not defects)
- `packages/client-python/docs/index.md:411-414` says "a few short attempts". Given F1 the honest number is "up to ~5 s". Per `AGENTS.md`'s co-located-documentation rule the doc is in the right place; only the number is wrong.
- `tests/test_pipe_open_retry.py:47-48, 63-64` monkeypatches `asyncio.sleep` **globally** rather than the module under test; `monkeypatch.setattr('rocketride.mixins.data.asyncio.sleep', …)` would be tighter.
- `test_open_does_not_retry_non_transient_failure` has no `monkeypatch` fixture, so if the predicate ever regressed to "retry everything" the test would take 0.75 s and still pass. Consider asserting elapsed time as well as `send_count`.

## 6. Compatibility and operational implications

- **API-compatible.** No signature change; `PipeException` is still what a genuine failure raises.
- **Latency:** worst-case `open()` — and therefore `send()`, `send_files()`, and the `async with client.pipe(...)` context manager — grows from ≈1.35 s to ≈4.8 s for a pipeline that never becomes ready (F1). This is the most important operational consequence and it is undocumented.
- **Diagnostics:** silent retries (F5) plus error substitution on disconnect (F4) make a slow `open()` harder to explain, not easier.
- **Resource safety:** no socket, timer or task leak. `asyncio.sleep` is the only new resource and is fully cancellable (E7); no server-side pipe or semaphore leak on the retried path (F7).
- **Platform:** the predicate's `'Connect call failed'` is CPython/asyncio wording, observed on macOS (`[Errno 61]`, E4) and reported on Linux (`[Errno 111]`, commit body). On Windows, `asyncio` connect refusals commonly read `ConnectionRefusedError: [WinError 1225] The remote computer refused the network connection`, which contains **neither** substring — so Windows is likely uncovered. CI builds Windows Server 2022. Not executable here; see Open question 1.
