**Scope correction — important.** The task hypothesis was “disconnect timeout guard rejects instead of resolving”, which reads as a change to the SDK's public `disconnect()`. It is not. `RocketRideClient.disconnect()` (`src/client/client.ts:1284` → `_detach(true)` at `:1097`) is **untouched**. This PR only changes how the *integration test suite* bounds its own teardown. Everything about the public disconnect contract below is therefore "unchanged by this PR", not "verified as changed".

## 2. Intended contract vs actual

**Intended.** Test teardown previously did:
```ts
await Promise.race([client.disconnect(), new Promise<void>((resolve) => setTimeout(resolve, 10000))]);
```
If `disconnect()` hangs, the timer *resolves*, teardown completes, and the suite proceeds as if cleanup succeeded — a real hang is invisible. The PR replaces this with a guard whose timer **rejects**, so a hang fails the test instead of being masked. It also clears the timer in a `finally`, which the inline version never did.

**Actual.** Both goals are met in principle and I verified the runtime semantics (§5). But as shipped the helper does not compile under the repo's own `ts-jest` configuration, so neither modified suite can execute at all (PR1002-F1).

**One inaccuracy in the stated intent.** The commit subject says the old guard was “swallowing errors”. It was not — `Promise.race` rejects as soon as `disconnect()` rejects, so *errors* always propagated. What the old form swallowed was the **timeout** (the hang). I verified this explicitly (§5 row 4): a rejecting operation propagates identically under both forms. The PR is still worth doing; the description just overstates what was broken.

**Production impact:** `RocketRideClient.test.ts` (the SDK's main integration suite, ~2000 lines) and `deploy.test.ts` both report **“Test suite failed to run”**. Net effect of merging as-is: the TypeScript client loses its integration coverage entirely — strictly worse than the masked-hang problem the PR set out to fix.
**Evidence:** reproduced deterministically with the repo's own jest config; see §5 rows 2–3. It is also the most probable cause of the 4 failing checks at head, though I cannot prove that (logs expired — §5).
**Introduced/worsened/pre-existing:** introduced.
**Smallest corrective direction:** one type change — make the rejector `Promise<never>`:
```ts
): { promise: Promise<never>; clear: () => void } {

```
`never` is absorbed by the union, so the race stays `Promise<T>`. **Verified**: with only that edit the suite compiles and all six of my characterisation tests behave as intended (§5 row 3).
**Regression-test criterion:** any suite importing the helper must run; more durably, a `tsc --noEmit` pass over `tests/**` in CI, since the build tsconfigs deliberately exclude tests and nothing else type-checks them.

### PR1002-F2 — P3 · confidence HIGH · introduced · documented convention violation

**Corrective direction:** copy the standard header block.

### PR1002-F3 — P2 · confidence HIGH · **intended** behaviour change, worth calling out explicitly
Teardown changes from “can never fail” to “fails on timeout”. That is the point of the PR, and I think it is right — a 10s hang in `disconnect()` is a real defect that should be loud. But two consequences deserve a conscious decision:
- A slow-but-successful disconnect on a loaded CI runner now **fails an otherwise-passing test**. `jest.config.js` sets `testTimeout: 120000` precisely because "CI runners can be slow", yet these guards are 10s/15s. Those budgets were chosen when blowing them was harmless; now they are hard failures.
- The failure surfaces in `afterEach`, so it is attributed to whichever test happened to run last rather than to the cleanup path — a confusing signal.
**Corrective direction (suggestion, not a defect):** raise the guard budgets to something clearly pathological (e.g. 30s/45s) now that exceeding them is fatal, and/or make the error message name the suite. The `${context} timeout ${ms}ms` message is already good — `disconnect timeout 10000ms` is instantly diagnosable.

### Explicitly checked and NOT defective
These were the highest-risk hypotheses going in. All were tested and all came back clean — recording them so they are not re-litigated:

- **Unhandled rejection from the orphaned operation — NOT a defect.** My initial hypothesis was that when the guard wins, the still-pending `disconnect()` promise is orphaned and a later rejection would be unhandled (potentially killing the jest worker). **Measured: 0 unhandled rejections** (§5 row 3). `Promise.race` subscribes a reaction to *every* input promise, so a late rejection is already handled even though the race settled long before. The hypothesis was wrong.
- **Timer leak on the success path — fixed, and this is a genuine improvement.** The old inline form never cleared its `setTimeout`, so each teardown held a 10–15s timer. The new `finally { guard.clear() }` clears it; verified with a `clearTimeout` spy (§5 row 3). Practical impact is modest because `jest.config.js` sets `forceExit: true`, which papers over lingering handles — but this removes a reason that flag is needed.
- **`makeTimeoutRejector` after `clear()`** — the promise stays pending forever and is GC'd; it never rejects, so no unhandled rejection from that side either (§5 row 3).
- **Is `timeoutGuard.ts` collected as a test suite?** No. `jest.config.js` `testMatch` is `['**/__tests__/**/*.+(ts|tsx|js)', '**/*.(test|spec).+(ts|tsx|js)']`; the filename matches neither, so there is no “Your test suite must contain at least one test” failure.
- **Public `disconnect()` contract — unchanged, so no caller needs new rejection handling.** `disconnect()` → `_detach(true)` is untouched. I surveyed all `.disconnect()` call sites under `apps/`, `examples/`, `packages/client-typescript`, `packages/shell` at develop (95 hits, of which the RocketRide-client ones are `apps/chat-ui/src/hooks/clientSingleton.ts:322`, `apps/dropper-ui/src/hooks/clientSingleton.ts:340`, `apps/test-ui/src/engine.ts:419,543,697,2018,2030`, `apps/vscode/src/auth/CloudAuthProvider.ts:208`, `apps/vscode/src/connection/connection.ts:143,198,607,683,933`, `apps/vscode/src/connection/deploy-manager.ts:214,263`; the rest are DOM `MutationObserver.disconnect()`). **None is affected by this PR.** Several already use `.catch(() => {})` best-effort handling, which is develop's existing posture.
- **Repeated / already-disconnected `disconnect()`** — governed by `_detach`'s `_lifecycleGeneration` / `_claimDisconnectedPublication` guards on develop; unchanged here, and out of this PR's scope.

If the latter, `disconnect()` can block for the full retry budget — and after #1002 lands, that would turn from an invisible teardown stall into a **hard test failure at 10s**.
