## 2. Intended behaviour vs actual implementation

**Bug (issue #1841).** Identical to #2004's: `send_files()` handed one coroutine per file to
`asyncio.gather()`, so a 500-file batch opened 500 pipes and 500 OS file handles at once (measured on
develop: 120 pipes / 120 fds for a 120-file batch, §5-A). Past the process fd limit, files fail as
`action: 'error'` entries rather than as a raised exception, so part of an upload is lost silently.

**Implementation.** `send_files(files, token, max_concurrent: int = 5)`. Validation at
`data.py:566-568` (bool excluded explicitly because `isinstance(True, int)`), placed after the empty-list
and token checks but still before any pipe is opened. The `gather` shape is kept: an
`asyncio.Semaphore(max_concurrent)` is created at `data.py:738` and an `upload_bounded()` wrapper
(`data.py:740-744`) holds a permit for one file's whole open/write/close cycle. `results` is still
pre-sized and index-assigned, so input order holds; `gather(..., return_exceptions=True)` is retained.

Two correctness changes beyond the bound:

* `file_size` is captured once inside the `try` (`data.py:637`, initialised to `0` at `:637`) and
  reused in the final event body (`data.py:712`), replacing develop's
  `os.path.getsize(filepath) if os.path.exists(filepath) else 0` — this removes a TOCTOU that could
  raise out of `upload_file`'s tail and leave a `None` hole in `results`.
* An explanatory comment at `data.py:698-703` records *why* a failed pipe is deliberately left open:
  `close()` is the finalize call (`data.py:253-306` — it flushes and commits), so closing a half-sent
  file would ingest a truncated document; there is no abort subcommand, so the pipe is left to the
  server's zombie reaper. Behaviour is unchanged from develop; the comment is the change.

CLI: a module-level `positive_int()` converter (`cli/main.py:79-87`) is used as
`--max-concurrent`'s `type=`, so `0`, `-1`, `2.5` and `five` are all rejected at parse time with one
message and exit code 2. `--threads`' help text is corrected to "Number of threads for pipeline
execution". `UploadCommand` forwards `self.args.max_concurrent` positionally (`upload.py:278`).

Docs: the three reference tables, the `send_files` signature section
(`ROCKETRIDE_python_API.md:530-541`), the "all files uploaded concurrently" example line (`:336`),
the **Performance Considerations** section (`:1113-1114`, which had claimed *"File uploads are
parallelized (all files uploaded concurrently)"* and *"The server handles queuing and rate limiting
automatically"*), and `types/data.py:169`'s `upload_time` comment (now "Seconds spent uploading this
file, excluding any wait for a free slot").

* Pre-existing, not introduced. Explicitly deferred by the author *"as agreed in review"*, and

* Regression-test criterion: assert
  `inspect.signature(DataMixin.send_files).return_annotation == List[UPLOAD_RESULT]`.

**PR1895-F2 — pending work is not bounded; the batch still creates one asyncio task per file.** (confidence: high — measured)

* `data.py:746-750` keeps the `upload_tasks = [...]` comprehension over all files and passes it to
  `gather`, so every file becomes a Task immediately; the semaphore only gates what they *do*.
* Measured (§5-A): peak live tasks is 41 for 40 files and 121 for 120 files, regardless of
  `max_concurrent`. #2004's worker pool holds it at `min(limit, n) + 1`.
* Practical impact is modest — `normalized_files` and `results` are O(n) either way, and every file is
  stat'ed during normalisation before any upload starts, so the batch already has O(n) memory. But at
  10⁵–10⁶ files the Task objects and their scheduler bookkeeping become the dominant cost, and each
  parked coroutine keeps its frame alive.
* Pre-existing shape, not a regression; the PR bounds the resource the issue named (pipes and fds) and
  leaves this one. Direction, if wanted without abandoning the semaphore: chunk the gather, or note
  the limitation in the docstring.

## 6. Compatibility + operational implications

* **Signature-compatible:** `max_concurrent` is the third positional-or-keyword parameter with a
  default. In-repo callers checked: `cli/commands/upload.py` (updated) and
  `packages/ai/src/ai/modules/mcp/engine.py:45`, whose `EngineClient` protocol declares
  `send_files(self, files, token) -> Any` — still satisfied.
* **Behaviour change, correctly flagged by the author** in the PR body: callers relying on unbounded
  parallelism now get 5. On a large directory, wall-clock can rise by roughly the ratio of the previous
  effective parallelism to 5, because each slot waits on `pipe.close()`, which blocks on server-side
  processing. joshuadarron raised the same point (item 5). Worth a release-note line.
* **`upload_time` semantics changed and documented:** it now measures from when the file acquires a
  slot, not from batch start, so it excludes queue wait. `cli/monitors/upload.py:229` renders it per
  file. `types/data.py:169` says so; anyone summing the field to estimate elapsed time under-reports
  by the queue time. This is the one place #1895 documents a semantic shift that #2004 leaves silent.
* **Doc debt paid:** the "Server handles queuing automatically" claim is removed from all five places
  it appeared, including the Performance Considerations section of the agent-facing reference.
* No new dependency; no change to the wire protocol or to `UPLOAD_RESULT`'s runtime shape.
