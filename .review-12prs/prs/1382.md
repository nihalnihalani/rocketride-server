## 2. Intended contract vs actual

**Intended.** Bound `sendFiles()` fan-out so at most `maxConcurrent` data pipes are open at once (default 5) instead of opening one pipe per file, preserve result ordering by index, keep per-file failures from killing the batch, and forward the CLI's existing `--max-concurrent` flag through to the client.

**The title's premise does not hold.** It says “implement **documented** maxConcurrent”, but `maxConcurrent` was not documented at the merge-base — this PR is what *adds* the doc rows to `docs/guide/index.md` and `docs/guide/methods/send.md`. (Confirmed: at the pinned develop, `grep maxConcurrent` over both files still returns **nothing** — see F3.) The real motivation is the Python SDK's `send_files(max_concurrent=…)` parity, not a pre-existing TS doc.

**Actual, on develop today.** `packages/client-typescript/src/client/client.ts:1762-1775` already implements the whole contract, and `src/cli/rocketride.ts:1461` already forwards `this.args.max_concurrent`:


### PR1382-F2 — P1 for merging as-is · confidence HIGH · would **regress** develop
**Where:** PR head `src/client/client.ts:1473-1474` vs develop `src/client/client.ts:1772-1775`
```ts
// #1382: invalid input is silently coerced
const requested = Number.isFinite(maxConcurrent) ? Math.floor(maxConcurrent) : 5;
```

**Expected vs actual:** resolving the conflict in the PR's favour would replace fail-fast validation with silent coercion — `sendFiles(files, token, 0)`, `-3`, `2.7` and `NaN` would all quietly become a different concurrency instead of raising. That is a strictly worse diagnostic posture for a public API and would undo a deliberate choice already merged.
**Production impact:** a caller who computes `maxConcurrent` from bad config gets an unexplained throughput change rather than an error.
**Introduced/worsened/pre-existing:** would be introduced by merging.
**Corrective direction:** do not port this validation. Develop's is better.
Two further behavioural deltas in the same direction: the PR downgrades the batch-error log from `console.error` to `this.debugMessage(...)` (**hides upload failures unless debug is on** — though `debugMessage` is the codebase's normal internal-diagnostic channel, so this is arguably a style improvement that should be argued on its own merits), and it clamps `limit` by `files.length || 1` where develop uses `Math.min(concurrency, files.length)` — functionally equivalent (both handle the empty-input case correctly; I traced `files = []` through both and each returns `[]` without opening a pipe).

### PR1382-F4 — P2 · confidence MEDIUM-HIGH · **pre-existing defect on develop** — the PR's one piece of genuine residual value
**Where:** develop `packages/client-typescript/src/client/client.ts:1865-1867`
```ts
    result = await pipe.close();
} catch (err) {
    error = err instanceof Error ? err.message : String(err);
}
```
**Trigger:** `pipe.open()` succeeds but `pipe.write()` (or the stream read) throws mid-upload — a truncated file, a transport hiccup, a server-side rejection.
**Expected vs actual:** the pipe should be closed on the error path; instead the `catch` records the message and moves on, leaving the pipe open. The same file's `send()` at `client.ts:1710-1722` already does the right thing:
```ts
} catch (error) {
    // Clean up pipe on any error
    if (pipe.isOpened) { try { await pipe.close(); } catch { /* Ignore cleanup errors */ } }
    throw error;
}
```
and so does the AI path at `client.ts:1948`. `sendFiles()` is the odd one out.
**Production impact:** a server-side pipe is held per failed upload until the connection drops. With a bounded pool this is now *worse* in one respect than the old unbounded code — a leaked pipe is not returned to the pool's accounting, and a batch with many mid-upload failures accumulates server-side resources.
**Introduced/worsened/pre-existing:** pre-existing on develop; #1382 is the only place it is fixed.
**Corrective direction:** port exactly the PR's added block into develop's `catch`, using the established `if (pipe?.isOpened)` guard so a failure that *was* `pipe.close()` is not re-closed. (`isOpened` is a real accessor at `client.ts:106`; the guard makes the double-close safe.)
**Regression-test criterion:** a unit test with a stubbed `DataPipe` whose `write()` rejects, asserting `close()` is called exactly once and that the returned `UPLOAD_RESULT.action === 'error'`.

- Signature `sendFiles(files, token, maxConcurrent = 5)`. **Default 5.**
- **Invalid input throws**: `!Number.isFinite || !Number.isInteger || < 1` → `RangeError('maxConcurrent must be a positive integer')`, raised *before* any pipe opens (`client.ts:1772-1775`). - **Peak active work** = `Math.min(concurrency, files.length)` workers, each claiming the next index from a shared counter; at most `maxConcurrent` pipes open at once.
- **Ordering**: results written by index, so `results[i]` always corresponds to `files[i]` regardless of completion order.
- **Partial failure**: per-file errors are captured into `UPLOAD_RESULT { action: 'error', error }` and the batch continues; an unexpected throw is caught per-worker and logged via `console.error`. **`sendFiles` never rejects for a per-file failure.**
- **Empty input**: `files = []` → `[]`, no workers, no pipes.
- **Cancellation**: there is **no** cancellation token or abort path in the TS implementation — worth checking whether Python's version offers one, since that would be a real API asymmetry.
- **Known gap (both may share it):** the TS `catch` does not close a pipe that failed mid-upload (F4). If `send_files` in Python has the same shape, it likely has the same leak — worth a look while you're in there.
