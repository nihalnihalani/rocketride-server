## 2. Intended behaviour vs actual implementation

**Intent.** `ExecutionMixin.get_task_status()` was annotated `-> TASK_STATUS` but returned the raw
dict from `self.call()`; the docstring described a third shape again (`state` as string literals
`'starting'`/`'running'`/`'failed'`, a `progress` dict, an `error` key) that matches neither the
annotation nor the wire payload. Three-way disagreement. The PR makes the annotation true at runtime.

**Implementation.** `execution.py:432-434`: `raw = await self.call('rrext_get_task_status', token=token)`
then `return TASK_STATUS.model_validate(raw)`. The docstring is rewritten to describe the real model
(`state` as a `TASK_STATE` int, `completedCount`/`totalCount`, `errors`, `exitCode`/`exitMessage`,
`metrics`/`tokens`). Five dict-style assertions in the integration suite are converted to attribute
access.

**Server contract (verified in-repo).** `cmd_task.on_rrext_get_task_status`
(`packages/ai/src/ai/modules/task/commands/cmd_task.py:254-296`) returns
`task.get_status().model_dump()`, and the server imports the *same* class from the SDK
(`packages/ai/src/ai/modules/task/task_server.py:87: from rocketride import TASK_STATUS, EVENT_TYPE`).
So on a matched build the round trip is exact. The docstring correction is right, and the annotation
was genuinely lying. **The diagnosis is correct; the remedy is what breaks.**

## 4. Confirmed findings

### P1

**PR2007-F1 — breaks the MCP `monitor` tool in the same build: `AttributeError: 'TASK_STATUS' object has no attribute 'get'`.** (confidence: high — reproduced)

* Break site: `packages/ai/src/ai/modules/mcp/tools/visibility.py:165`
  (`state = status.get('state', 0)`), reached on the first poll of `_monitor`.
  Eight further `.get()` calls on the same value at `:107, 111, 112, 122, 123, 124, 126, 127`.
* The value is produced at `visibility.py:152`:
  `status = await asyncio.wait_for(client.get_task_status(token), timeout=per_poll_timeout) or {}`,
  where `client` is a `RocketRideClient`: `packages/ai/src/ai/modules/mcp/engine.py:103-105`
  (`from rocketride import RocketRideClient` … `self._client = RocketRideClient(uri=uri, auth=auth)`),
  and the seam's own protocol declares `async def get_task_status(self, token: str) -> Dict[str, Any]`
  (`engine.py:53`).
* Same build, not a downstream package: `packages/client-python/scripts/tasks.js`
  (`makeSyncClientPythonAction`) syncs `packages/client-python/src/rocketride` into
  `dist/server/rocketride`, which is the `rocketride` the engine imports. Changing the SDK's return
  type changes the engine's behaviour in the same release.
* Expected: `monitor` polls and returns a snapshot. Actual: the MCP tool raises `AttributeError`,
  which `_monitor`'s `except Exception` at `:158` converts into `normalize_error(exc)` — i.e. every
  `monitor` call becomes an error envelope. `list_running_pipelines` is unaffected.
* Production impact: the MCP `monitor` tool is the documented way an agent waits for a pipeline
  (`visibility.py:11`: *"a **bounded poll** of `get_task_status`"*). It stops working entirely.
* Evidence: §5-C, case 2. Introduced by this PR.
* Why CI does not catch it: every MCP test substitutes a fake engine that returns plain dicts
  (`packages/ai/tests/ai/modules/mcp/test_engine.py:237` `async def get_task_status(self, token: str) -> dict`;
  `conftest.py:238`). **A green CI here is not evidence of safety.**
* Smallest corrective direction: either keep returning a dict and fix the annotation + docstring
  instead (the minimal reading of #1988), or update all nine `.get()` sites in `visibility.py` to
  attribute access in the same PR. The `'status': status` field at `visibility.py:121` also needs a
  `model_dump()` or the MCP tool result stops being JSON-serialisable.
* Regression-test criterion: an MCP `monitor` test whose fake engine returns what
  `RocketRideClient.get_task_status` actually returns (a `TASK_STATUS`), not a hand-written dict.

**PR2007-F2 — breaks the `GET /task/status` REST endpoint: `ResultSuccess.data` is typed `Optional[dict]`, and a BaseModel does not validate into it.** (confidence: high — reproduced)

* Break site: `packages/ai/src/ai/modules/task_http/task_status.py:42` (`return response(status)`),
  landing in `packages/ai/src/ai/web/response.py:70` (`content = ResultSuccess(data=data, …)`)
  against `ResultSuccess.data: Optional[dict] = None` (`response.py:32`).
* Pydantic v2 raises `ValidationError: Input should be a valid dictionary`. `task_status.py`'s
  `except Exception as e: return exception(e)` swallows it, so the endpoint returns an **error
  envelope instead of the task status** — a silent outage rather than a crash.
* **The PR body's safety argument is wrong on the field type.** It says the result *"passes straight
  into `response()` — confirmed this is safe since `model_dump()` recursively serializes nested
  pydantic models even under an `Any`-typed field"*. `data` is not `Any`; it is `Optional[dict]`, and
  the failure happens on the way *in*, before any `model_dump()`.
* Evidence: §5-C, case 3. Introduced by this PR.
* Why CI does not catch it: `packages/ai/tests/ai/modules/task_http/test_simple_endpoints.py:83`
  mocks `client.get_task_status = AsyncMock(return_value={'state': 'RUNNING', 'name': 'task-1'})`.
* Corrective direction: `return response(status.model_dump())` at `task_status.py:42`, in this PR.
* Regression-test criterion: an endpoint test whose mock returns a `TASK_STATUS` instance.

### P2

**PR2007-F4 — new server fields are now silently dropped instead of reaching the caller.** (confidence: high)

* `packages/client-python/src/rocketride/types/task.py:295` — `TASK_STATUS` declares no
  `model_config`, so pydantic v2's default `extra='ignore'` applies.
* Trigger: SDK older than the server (routine — the SDK is versioned and published separately,
  `pyproject.toml` version 1.3.0). A field the server adds to `TASK_STATUS` is dropped by the client
  with no warning, where before this PR the caller received it in the dict.
* Measured (§5-C, case 4): `queuePosition` present in the payload, absent from the validated model.
* Production impact: forward compatibility is lost. A user script reading a newly-shipped status
  field starts seeing nothing, with no error to point at the cause.
* Introduced by this PR. Direction: set `model_config = ConfigDict(extra='allow')` on `TASK_STATUS`
  so unknown fields survive as extras, and say so in the docstring.

**PR2007-F5 — a `null` in any field turns a status poll into an opaque `ValidationError`, which is a new exception type escaping the public API.** (confidence: high)

* `execution.py:434` (`TASK_STATUS.model_validate(raw)`).
* Measured (§5-C, case 5): `state: null` → `ValidationError at state: Input should be a valid
  integer`; `errors: null` → *"Input should be a valid list"*; `metrics: null` → *"Input should be a
  valid dictionary or instance of TASK_METRICS"*. Every field in `TASK_STATUS` has a default, so a
  *missing* key is fine — but an explicit `null` is not, and a mismatched or proxied server can send
  one.
* The method's `Raises:` section still says only `RuntimeError: If status retrieval fails`. Callers
  doing `except RuntimeError` around a poll loop now get an unhandled `pydantic_core.ValidationError`.
  That is a public-API compatibility change and it is undocumented.
* Introduced by this PR. Direction: catch `ValidationError` and re-raise as the SDK's own error type
  with the raw payload attached (diagnosability is the point of the change), and document it.

**PR2007-F6 — three docs still declare the old return type; none is in the diff.** (confidence: high)

* `docs/README-python-client.md:203` — `async def get_task_status(self, token: str) -> dict` / column `dict`.
* `packages/client-python/docs/index.md:206` — identical row.
* `docs/agents/ROCKETRIDE_python_API.md:468` — `##### async get_task_status(token: str) -> Dict[str, Any]`.
* `docs/README-python-client.md:408,465`, `docs/agents/ROCKETRIDE_python_API.md:996,1001` and
  `docs/agents/ROCKETRIDE_QUICKSTART.md:90` all show dict-style usage of the result.
* `docs/agents/ROCKETRIDE_python_API.md` is the file agents are pointed at before writing RocketRide
  code, so leaving it stale actively produces broken generated code.
* Introduced by this PR (the divergence is new; before the PR the docs matched the runtime).

### P3

**PR2007-F7 — `TASK_STATE(status.state)` is not safe for a state the client does not know.** (confidence: high)

* The rewritten docstring tells callers *"Compare 'state' against TASK_STATE enum members, not
  strings"*. `state` stays a plain `int` after validation, so an unknown value passes through
  (measured: `state: 99` validates fine) — but `TASK_STATE(99)` raises `ValueError: 99 is not a valid
  TASK_STATE` (§5-C, case 6). The docstring should say to compare against `TASK_STATE.X.value`
  (which its own example does) and warn that constructing the enum from the wire value needs a guard.

**PR2007-F8 — the only tests touched are integration tests that cannot run without an engine.** (confidence: high)

* All five edits land in `packages/client-python/tests/RocketRideClient_test.py`, which needs a live
  server (`conftest.py:70-79` connects a real client). There is no offline unit test asserting that
  `get_task_status` returns a `TASK_STATUS`, that a realistic payload validates, or that consumers
  still work. A pure-Python test with a stubbed `call()` would cost a few lines and would have caught
  F1/F2 if extended to the consumers.

## 6. Compatibility + operational implications

* **Public API break.** `get_task_status()` returns a different Python type. Any caller doing
  `status['state']`, `status.get(...)`, `json.dumps(status)`, `dict(status)` or `**status` breaks.
  Two such callers exist inside this repository (F1, F2); external SDK users are unmeasurable but the
  documented usage is dict-style in five places (F6).
* Not flagged as breaking: the PR checklist has no breaking-change note and `CHANGELOG.md` is untouched.
* **TypeScript divergence.** `packages/client-typescript/src/client/client.ts:1633` does
  `return await this.call<TASK_STATUS>('rrext_get_task_status', …)` — a *typed view over a plain
  object*, with no runtime validation. After this PR the two SDKs differ not only in typing strategy
  but in runtime failure modes (TS silently accepts a malformed payload; Python raises).
* **Positive:** on a matched build the round trip is exact and the docstring becomes true. The
  underlying complaint in #1988 is real and worth fixing.

## 8. Unresolved questions

1. Which side of the contract is meant to be authoritative — is `get_task_status` supposed to return
   a validated model (and the two `packages/ai` consumers should be updated), or a dict (and #1988 is
   a docstring/annotation fix)? The TypeScript client returns an unvalidated typed object, which
   argues for the smaller fix.
2. If the model is kept: should `TASK_STATUS` become `extra='allow'` so the client stays
   forward-compatible with newer servers (F4)?
3. Should `ValidationError` be wrapped in an SDK exception type? Related to #2011's F4 (the SDK has an
   unused exception hierarchy).

## 9. Verdict — **CHANGES REQUIRED**

The diagnosis in #1988 is correct and the docstring rewrite is a genuine improvement. But the chosen
remedy changes a public return type and breaks two consumers **inside this repository** — neither
covered by tests, because both suites fake the SDK with dicts — and CI is red on an unused import.

Remaining work:

1. Decide §8 Q1 with a maintainer. The lowest-risk option is to keep the dict, change the annotation
   to `Dict[str, Any]`, and keep the docstring rewrite; that closes #1988 with no breakage.
2. If the typed return is kept:
   * update all nine `status.get(...)` sites in `packages/ai/src/ai/modules/mcp/tools/visibility.py`
     and serialise `'status': status` in `_snapshot` (F1);
   * `return response(status.model_dump())` in
     `packages/ai/src/ai/modules/task_http/task_status.py:42` (F2);
   * add `model_config = ConfigDict(extra='allow')` to `TASK_STATUS` (F4);
   * wrap `ValidationError` and document it in `Raises:` (F5).
3. Remove the unused `TASK_STATE` import (F3) — required either way.
4. Update the three doc entries and the five dict-style examples (F6) — required either way.
5. Add an offline unit test for `get_task_status` with a stubbed `call()`, and switch the MCP/HTTP
   test fakes to return whatever the SDK really returns (F8) — this is the test that would have
   caught F1/F2.
