The mechanics are genuinely solid — the TS writer and Python reader agree byte-for-byte on the discovery format (executed both), readiness ordering is right (port bound before the file appears), and explicit `uri`/env always win. Two P1s and three smaller items before this merges:

1. **Credential redirect (reproduced independently twice).** The discovery file is trusted without constraining the host: with `ROCKETRIDE_APIKEY` in env and a discovery file naming `wss://attacker.example.com:5565`, `RocketRideClient()` connects there carrying the real key — and if the file also supplies an `apiKey`, that is adopted too, so the file controls the client's entire connection identity. The parser (`_connection_discovery.py:115`) only checks "non-empty string + int pid". Fix direction: require loopback (or an explicit allowlist) before adopting a discovered URI, and ignore the file otherwise.
2. **Windows liveness probe.** `os.kill(pid, 0)` in `_connection_discovery.py:86-99` is POSIX-only — on Windows, CPython routes non-CTRL signals through `TerminateProcess`, so the probe can kill an unrelated process and `ProcessLookupError` never fires (dead PIDs read as alive → stale files adopted). Your own TS side does this correctly with `process.kill(pid, 0)`; the Python side needs a platform-aware check.
3. Smaller: the reader silently adopts the hardcoded `'MYAPIKEY'` placeholder (`engine-local.ts:454` writes it, acknowledged in the comment above it); the discovery file is written 0644 (`engine-local.ts:450` passes no `mode`) — worth `0o600` as defence-in-depth since this file influences where a credential is sent, even though today's payload is only the public local default; `ROCKETRIDE_URI=''` no longer raises the invalid-URI error develop raises; and the silent cloud→localhost default change isn't reflected in `packages/client-python/docs/index.md` (AGENTS.md co-location rule).

With the loopback constraint and the platform fix, this is a strong QoL feature.
