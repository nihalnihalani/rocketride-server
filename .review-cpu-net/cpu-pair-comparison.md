## What #1697 actually requires (from the full issue + comments)

1. The measured problem is the **whole CUDA footprint** on CPU-only hosts: 6.6 GB of 8.2 GB site-packages = nvidia-* 4.3G (all of it torch's dependency set) + torch 1.7G + triton 639M, rewritten **on every pod start**.
2. Root cause (author's own later correction, 2026-07-29): **not transitive**. `packages/ai/src/ai/common/torch/requirements.txt` explicitly pins `torch==2.10.0+cu128; platform_system != 'Darwin'` and `torchvision==0.25.0+cu128` behind `--extra-index-url .../whl/cu128`; `REQUIREMENTS_GLOBS` (`ai/**/requirement*.txt`) sweeps it into every constraints compile, and `-c constraints.txt` applies it to every node install. Verified present at develop `9a5fc5c8` AND at both merge-bases.
3. Second, **latent** source: `onnxruntime-gpu==1.22.0; platform_system != 'Darwin'` declared directly by `nodes/src/nodes/anonymize/requirements.txt` and `nodes/src/nodes/audio_transcribe/requirements.txt` (installs when those nodes first run). Resolver-verified (T8): ORT-gpu 1.22.0 pulls **no** nvidia-* pip packages — the payload is the ORT-gpu wheel itself, not a second nvidia tree.
4. Constraints on any fix: opt-in / default-off (GPU self-hosters must be untouched); and the issue leaves "should the engine grow a first-class CPU-resolve mode" explicitly open — the cloud could instead overlay a CPU-pinned copy of the one file via the SaaS image.
5. **Outstanding for any rollout** (stated three times in the issue): functional verification that the four torch nodes actually run on `torch+cpu`. Neither PR provides it; neither could I (level-5 unavailable here).

So the required outcome is: **CPU torch (incl. torchvision) = the 6.6 GB; ONNX handling = a latent extra**; both behind an opt-in. A fix that leaves `nvidia-*` resolving in fails the core ask.

### #2003 "fix(depends): opt-in PyTorch CPU index to avoid CUDA on CPU-only hosts" — KESHAV8087, head `880f743f9`, +105/−10, 2 commits, 79 behind develop

Mechanism: `ROCKETRIDE_TORCH_CPU`; `_torch_cpu_index_args()` (line 348) adds the CPU index as a **CLI arg**, and `_torch_cpu_overrides_file()` (lines 358–398) scans all requirement files with `^\s*(torch|torchvision)\s*==\s*([0-9][0-9.]*)\+cu\w+` (IGNORECASE), derives `+cpu` overrides from the discovered `+cu` pins into `cache/torch-cpu-overrides.txt`, and both are threaded through **all three** uv invocations — `_compile_constraints` (794–795), `_install_dry_run` (913–914), `_install_requirements_inner` (1018–1019). `_compute_hash` seeds the **raw** env value (line 738). The 2nd commit (`880f743f`, responding to CodeRabbit's line-350 Major) added the overrides + cache-key; the 1st commit alone had #1708's identical dead-end (index without overrides).

Compile/dry-run/install parity is by construction (same helper args at all three sites) and the compile-emitted indexes additionally reach install consumers via `-c` (T6 proved uv 0.11.25 honors `--extra-index-url` lines inside a constraints file).
- **Darwin hard break — P1, the standing unresolved review item.** The pin scan is text-level, not marker-aware, so on a Mac it still finds the non-Darwin `+cu128` lines and writes marker-less `torch==2.10.0+cpu` overrides; no macOS `+cpu` wheels exist (T4: "no wheels with a matching platform tag", hint lists linux/windows only) → compile fails → `ensure_constraints()` raises → since `rocketlib/types.py:31` calls `depends()` at import time, **engine startup breaks** on any Mac with the flag set. Setting a "CPU" flag on a Mac is a natural act; the failure is hard, not silent.
  **Caution for the fixer:** CodeRabbit's literal suggestion (preserve the source marker on each override) is subtly wrong under uv's override semantics — T12b shows an override whose marker is false **replaces the declared requirement with nothing**: on Darwin, marker-carrying `+cpu` overrides silently DELETE torch/torchvision from the resolve (empty lock) instead of falling back to the plain pin. The correct smallest fix is to make the flag inert on Darwin (return disabled from the helpers when `platform.system() == 'Darwin'`), where default wheels are already CPU.
- Override generation robustness (all level 1, via the real imported helpers): exact-pin forms only. Comment lines correctly skipped; `torch==2.10.0.post1+cu128`, `torch==2.10.*+cu128`, `torch>=2.10+cu128`, and direct-URL refs are silently unmatched → flag silently keeps CUDA if the pin ever changes shape (today's in-tree pin is exactly the matched shape, so this is fragility, not a live defect). Conflicting pins across files resolve first-wins in `glob()` discovery order, which Python does not guarantee sorted — order-dependent output (no conflicting pins exist in-tree today). Unreadable file → silently skipped. torchaudio not covered — and **no torchaudio exists anywhere at develop** (verified), so correctly out of scope today.
- Raw-value hashing (line 738): `1`/`true`/`yes`/` 1 ` produce four distinct hashes; `0` vs unset differ too → spurious constraint rebuilds between equivalent spellings. Over-invalidation only — every behavior change still changes the hash, so **correctness holds** (probes, level 1). Not a blocker; polish.
- Unrelated churn: 8 hunks of em-dash→hyphen edits, including the **user-visible** `monitorStatus(f'Waiting — {detail}')` string, plus comment/docstring edits far from the feature. One of develop's three merge conflicts is caused purely by this churn colliding with the new satisfied-verdict cache (see integration below) — and a careless "take PR side" resolution there would delete develop's verdict-cache check.
- CI: **never ran** at either commit (only Auto-label/discord/CodeRabbit in the rollup) — no Ruff, no build. I ran ruff 0.14.4 check+format with the repo's pyproject config over the head blob: clean. Still, the head is CI-unverified.
